# PTS Report WT3VX7WG Review

Date: 2026-05-30

Verdict: `PARTIAL_BUSINESS_EVIDENCE`, not valid PTS performance evidence.

`WT3VX7WG` did reach the backend, unlike `TR3VX7RG`, but it still cannot be used
as the accepted-ladder performance baseline.

PTS overview:

- report id: `WT3VX7WG`;
- time: `2026-05-30 01:44:05` to `2026-05-30 01:45:05`;
- `AgentCount=2`;
- `Vum=967`;
- `POST PTS-1 hotspot bid` samples reported by PTS: `196`;
- PTS success rate: `100%`;
- PTS p99: about `43.9ms`.

Server-side business truth:

- DB unique bids: `1000`;
- accepted: `669`;
- rejected: `331`;
- `auc_live.current_price_cents=8020000`;
- `auc_live.accepted_bid_count=669`;
- `auc_live.seq=669`;
- `auc_live.engine_seq=1000`;
- `outbox_events=669`;
- `auction_events=669`;
- DLQ empty;
- Kafka consumer lag zero;
- Redis pending decisions empty;
- all correctness/invariant gates passed.

Why it is not valid performance evidence:

1. PTS only reported `196` POST samples while PostgreSQL recorded `1000` business
   bids. The PTS latency and TPS numbers therefore describe only a truncated
   part of the one-shot workload.
2. The DB bid window was about `10.046s`, from `2026-05-29 17:44:58.917277+00`
   to `2026-05-29 17:45:08.96307+00`, extending beyond the 1-minute PTS report
   end. The scene still ended too close to the business traffic tail.
3. The CSV was generated by lexical `ORDER BY id`. The first 1000 rows were not
   the numeric first 1000 `k6_bidder_{bucket}_{lane}` users. Because the JMX
   rank formula derives release offset from `bucket/lane`, selected users with
   large bucket numbers stretched a nominal 5ms/1000-bid ladder beyond the
   intended 5-second window.
4. Two PTS agents can still introduce local ordering jitter. The run had `268`
   amount inversions by arrival order, and lower prices arriving after a higher
   price were correctly rejected by the monotonic-price rule.

What it proves:

- The Redis/Kafka/PG/outbox pipeline settled `1000` ledger decisions without
  gaps, duplicates, pending work, DLQ, or lag.
- The low-price rejection rule behaved correctly under arrival reordering.
- It does not prove accepted hot-path capacity because only `669/1000` bids were
  accepted and PTS truncated the sampler report.

Fix:

- `docs/perf/pts/generate-pts-sessions.sql` now orders `k6_bidder` users by
  numeric bucket and lane before writing the CSV. With `SESSION_COUNT=1000`, the
  accepted-ladder JMX rank formula now maps the selected users to ranks `1..1000`
  instead of allowing lexical ordering to pull in high-rank users.
- The accepted-ladder JMX now uses `burst_wait_ms=40000` with
  `accepted_barrier_quantum_ms=10000`. This keeps the cross-agent wall-clock
  alignment benefit of the 10-second quantum while avoiding the 60-second scene
  boundary failure seen in `TR3VX7RG`.
