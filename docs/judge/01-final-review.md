# 直播竞拍全栈系统 · 评委阅读版

> 参赛作品：抖音电商 AI 全栈挑战赛  
> 文档日期：2026-06-10  
> 阅读定位：项目总览、核心技术亮点、S1-S5 证据边界和答辩口径

## 一句话结论

这是一套围绕直播竞拍“最后一秒高并发、强一致出价、断线恢复、异常失败关闭”构建的全栈系统。核心链路不是简单的 WebSocket demo，而是：

```text
Redis Lua 单写者原子决策
  -> Kafka 有序决策 WAL / Fence
  -> PostgreSQL 结算 / 审计 / 订单真相
  -> Reconciler 校验闭环
  -> Outbox / WebSocket 实时投递
```

系统目标是让用户看到的每一次出价结果都能追溯到服务端决策、持久化状态和结算真相；在 Redis/Kafka/PostgreSQL 或网络异常下，系统优先失败关闭，不凭空接受出价。

## 核心亮点

| 维度 | 设计 |
|---|---|
| 热出价路径 | Redis Lua 在单个原子脚本内完成幂等、状态校验、ACL、价格网格、封顶成交、反狙击延时、误触确认和 `engine_seq` 递增 |
| 持久性 | Kafka 记录有序决策 WAL；PostgreSQL 承担结算、审计、订单和 exactly-once 业务边界 |
| 一致性 | Reconciler 对 Redis/Kafka/PostgreSQL/Outbox 做漂移检测；状态不完整时进入 `RECONCILING` |
| 实时体验 | H5 端服务器权威，不做乐观成功；倒计时以服务端时间为锚；WebSocket 断线后通过序号和快照恢复 |
| 竞价规则 | 0 元起拍、加价幅度、封顶自动成交、10-30 秒反狙击延时、主播取消、误触二次确认 |
| AI 能力 | 选品 Copilot、商品 Q&A、直播解说、哨兵告警、复盘高光；AI 只做助手和叙述者，不决定价格、胜者或终态 |

## S1-S5 评测主线

| 场景 | 证明的问题 | 关键指标 |
|---|---|---|
| S1 绝杀时刻 | 1000 用户最后一秒竞争同一拍品时，决策是否快且正确 | bid decision p99 <= 60ms；最高有效价胜出；每个拒绝有依据 |
| S2 正常竞价 | 稳态出价、结算收敛和资源稳定性 | 决策 p99、读接口 p99、Kafka/PG/Outbox 收敛、资源曲线稳定 |
| S3 万人围观 | 单房间广播和连接保持能力 | fanout p99 <= 1s；连接数保持；内存/连接成本 |
| S4 故障韧性 | Redis/Kafka/PG/worker 故障下是否失败关闭且无重复结算 | RTO、RPO=0、无 phantom accept、无 double charge |
| S5 断线重连 | 弱网/断线后用户能否恢复到当前状态 | time-to-current-state、无丢失/重复通知 |

## 答辩口径

- 为什么不用 PostgreSQL 行锁做热路径：同一拍品最后一秒 1000 并发会集中竞争单行，行锁串行化不适合低尾延迟；PostgreSQL 保留为结算和审计真相。
- 为什么需要 Kafka：Kafka 是决策 WAL、重放源和结算 fence，不是装饰性中间件；它让 Redis 热态和 PostgreSQL 结算之间有可重放、可校验的有序边界。
- 为什么可以说“AI 安全”：AI 不参与出价裁决、胜者判断、终态写入和扣款；所有 AI 输出都锚定已发生事实或待人工确认的商家草稿。
- 如何面对性能证据边界：仓库保留 S1-S5 方法、指标和校验门禁；大体积 raw evidence 不提交。正式性能数字需要按 `tests/pts/` 与 `tests/load/` 复跑并附报告。
