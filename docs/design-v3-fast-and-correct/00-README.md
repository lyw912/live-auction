# Design v3 — 又快又对：单写者决策日志架构（Single-Writer Decision Log）

> 状态：独立评审组提出的目标架构方案，2026-05-31。
> 目的：一次性跳出「快但错 ↔ 对但慢」的循环，让 PTS-1B 在**用户可见最终决策 p99 ≤ 50ms** 的同时，
> 保证**绝对正确性**、**durable ledger/settlement 闭环**，并**完整通过故障注入**。
>
> 本方案**不是补丁、不设 mode、不做新旧并行**。它是一次有明确不变量证明的架构纠正，
> 替换当前热路径中那个被错放的同步串行环节。

---

## 0. 一句话结论（评委先看这句）

当前系统**决策是对的、也是快的**（Redis 单线程 Lua 原子定序），
但它把**持久化**（Kafka append）以「**严格按 engine_seq 顺序、单拍品一把锁、同步等 ack**」的方式
**钉死在热路径上**——于是它在比 PG 行锁低一层的地方，**亲手重建了同一个「几百人抢一行」的串行瓶颈**。
这就是 1000 个请求全返 `202`、只有 300 个落库（HA5YX7ZG）的根因。

**修复只有一招，但要做彻底**：把「定序/决策」和「持久化/结算」彻底解耦——
决策仍在 Redis 单写者内同步完成并立即返回最终结果；
持久化改为**组提交（group commit）的异步有序中继**，绝不再上热路径锁；
结算改为**按 `engine_seq` 幂等投影**到 PostgreSQL，**删除**结算回写 Redis 的逻辑（那正是 HA5YX7ZG 的污染源）。

这正是金融撮合引擎 / LMAX / 事件溯源的标准做法：**「引擎永远跑在持久化前面，WAL 在后面异步追上」**。

## 2. 三个角色：当前架构把它们混为一谈，这是一切问题的源头

| 角色 | 职责 | 谁来承担（v3） | 当前实现的错误 |
|---|---|---|---|
| **决策权威（Decision Authority）** | 谁赢、定序、原子、幂等 | Redis 单线程 Lua CAS（已正确） | 正确 ✔ |
| **持久性（Durability）** | 决策不因崩溃丢失 | 追加式**决策日志**：Redis Stream → 组提交中继 → Kafka | ❌ 同步、按序、单锁地钉在热路径 → 重建瓶颈 |
| **结算/系统真源（System of Record）** | 钱、订单、审计、查询 | PostgreSQL，作为决策日志的**幂等投影** | ❌ 结算 worker 反向回写 Redis 活状态 → engine_seq 重用 → 污染 |

> **关键认知**：「**谁是持久真源（PG）**」与「**谁在实时拍板（Redis 单写者）**」是**两个不同的角色**。
> 把拍板权放进 Redis，**不等于**放弃 PG 作为持久真源，**也不削弱正确性**——
> 只要每个决策 (1) 单写者原子定序、(2) 在能影响钱之前已写入追加式日志、(3) 幂等结算进 PG。详见 `02` 第 4 节。

## 3. v3 热路径（用户在 50ms 内经历的全部）

```
出价点击
  → 网关：鉴权 / 房间 ACL / 防抖·令牌桶 / 幂等快路径   （便宜，不读 PG 热行）
  → Redis Lua CAS（一次原子调用，单写者）：
        幂等去重 → 全部竞拍规则 → 分配无间隙 engine_seq
        → 更新 价/赢家/结束时间 → XADD 写入决策日志流
  → 立即返回最终结果：
        result: ENGINE_ACCEPTED | ENGINE_REJECTED | ENGINE_SOLD
        decision_status: DECIDED          ← 用户可见的最终业务决策（p99 ≤ 50ms 测这个）
        durability_status: ENGINE_DURABLE ← 已在 Redis 日志+副本；稍后转 KAFKA_ACKED
        settlement_status: PENDING        ← 稍后转 SETTLED
```

热路径**没有**同步 Kafka、**没有**同步 PG、**没有**单拍品 append 锁。
决策在 Lua 提交的那一刻就是**最终且权威**的（确定性、有序、幂等、已落追加日志）。

**持久化在关键路径之外**：单个有序中继**批量**把决策流灌进 Kafka（一次批量 produce，幂等 producer，
按 auction 分区保序）——**这就是组提交**：1000 个决策 → 几次批量写 → 全部在 ~10–30ms 内 Kafka 落定，
然后通过 WebSocket 把 `已确认` 推给前端。**没有逐笔锁。**

## 4. 与评分表的对应（详见 `06`）

- **技术实现与工程完整度（50%）**：全链路闭环（采集→决策→定序→持久→结算→实时推送），
  可用性（断连重连/异常兜底/fail-closed）、**性能（p99≤50ms 同步最终决策）**、稳定性（防击穿/数据一致性/对账）、可观测性（三维状态指标+告警）。
- **技术深度与创新性（25%）**：选型与「单热点强一致 + 毫秒实时」场景的硬核适配——
  单写者决策日志、组提交持久化、effectively-once 结算（fencing token + 条件更新 + 幂等键）、
  房间级 WS 路由隔离、按 `engine_seq` 的幂等与防重复扣款。
- **加分项·高并发架构硬核优化**：Redis 分层（决策态/幂等/日志流）+ 读写分离、**绝不一笔扣两次钱**（幂等键 + fencing + 唯一约束三层）、单拍品 1000+ 在线（WS 房间路由 + 合并广播）。

## 5. 当前 vs v3（一图胜千言）

```
当前（快但错 / 对但慢）：
  Lua 决策(快) ──→ waitForPendingAppendTurn(按 engine_seq 排队)
                     └─ SetNX 单拍品锁 ─→ 同步 Kafka append(等 ack) ─→ 返回 ENGINE_*
                        │ 抢不到锁 / 不是最小 seq
                        └────────────────────────────────────────→ 返回 202(绝大多数)
  结算 worker ──→ refreshRedisSettledState(把 PG 旧快照写回 Redis) ─→ engine_seq 重用 ─→ 污染/暂停

v3（又快又对）：
  Lua 决策+XADD(原子, 单写者) ─→ 立即返回 DECIDED(最终)         ← 50ms 在这里结束
        │
        └─(关键路径之外) 单中继批量 ─→ Kafka(组提交,保序) ─→ PG 幂等投影(按 engine_seq) ─→ WS 推送"已确认"
                                                              └─ 收盘: fencing+条件更新+幂等键 ─→ 唯一成交/唯一扣款
  结算 worker：只写 PG，**永不回写 Redis 活状态**
```

后续每个文件把上面的每一句都展开成「可落地 + 经得起拷打」的细节。
