# 06 — 与宣讲版评分标准逐条对应

> 逐字逐词对照 `抖音电商AI全栈课题-直播竞拍全栈系统（宣讲版）.md` 的功能范围、两大挑战、加分项、评分维度。
> 主要聚焦性能，但每条都答到正确性/可用性/稳定性，确保「又快又对」可被评委直接打分。

## 1. 两大核心挑战

### 挑战一：复杂规则的逻辑攻坚（零漏洞）

| 规则 | v3 如何零漏洞实现 |
|---|---|
| 0 元起拍 | Lua：`accepted_bid_count<=0` 时基准用 `start_price`（含 0） |
| 加价幅度 | Lua：`(amount-base)%increment==0` 且 `amount≥base+increment`，否则 `BID_INCREMENT_MISMATCH`/`BID_TOO_LOW` |
| 封顶价 | Lua：`amount==cap → ENGINE_SOLD` 原子置终态；`>cap → BID_ABOVE_CAP` |
| 自动延时 | Lua 窗口内原子延长 + **绝对天花板**（新增）；服务端单调时钟；WS 毫秒级重置 |
| 异常取消 | 主播取消走原子状态转换 + fencing，后续出价被 fence；终态唯一 |

全部在**单次原子 Lua** 内完成 ⇒ 无半应用脏读，无「刚好过线」竞态。对应调研 §6.2.1 工业级行。

### 挑战二：毫秒级实时同步

| 要求 | v3 对策 |
|---|---|
| 出价秒级同步、排名一致 | 服务端权威态 + 按 engine_seq 全序；WS 房间级广播；合并窗口防广播风暴 |
| 倒计时毫秒级无偏差 | 仅信服务端 `now_ms/end_at_ms`；客户端纯动画；延长后广播重置 |
| WS 稳定、自动重连 | 心跳保活 + 断连按 engine_seq 拉 snapshot+增量 diff，无跳变 |
| 不延迟/卡顿/排名错乱 | **决策 p99≤50ms 同步最终**；全序消除错乱；虚拟列表防 DOM 爆炸 |

## 2. 功能模块闭环（技术实现与工程完整度，权重 50% 的主体）

> 「从竞拍数据采集 → 数据治理 → 后端服务（出价校验、状态机管控）→ 接口网关 → 前端交互」的**顺畅闭环度**。

```
采集(出价/行为) → 网关(鉴权/限流/幂等) → Redis 单写者决策+定序+WAL日志
   → 组提交中继 → Kafka 决策总线 → 结算幂等投影 PG(订单/审计) → outbox/WS 实时反馈/氛围动画
   → 断连重连 snapshot+增量 → 闭环
```

- 商家端：竞拍发布/规则配置/商品管理/订单管理 → 规则进 Lua 决策态；订单由收盘 effectively-once 生成。
- 用户端：直播间/浏览/出价/排名/被超越提醒/延时提醒/结束提醒/成交/模拟支付/历史 → 全部由服务端权威事件驱动。

## 3. 评分维度表（逐条）

| 维度 | 权重 | v3 命中点 |
|---|---|---|
| **技术实现与工程完整度** | 50% | 全链路闭环（上图）；**可用性**：断连重连、异常兜底、fail-closed；**性能**：最终决策 p99≤50ms（同步，非 202）；**稳定性**：缓存防击穿（Lua 内 PG 冷快照单飞 seed + 幂等）、数据一致性（单写者+幂等投影+对账）；**可观测性**：三维状态指标、Redis/Kafka/PG 诊断、对账缺口告警 |
| **技术深度与创新性** | 25% | 选型与「单热点强一致+毫秒实时」**精准适配**：单写者决策日志、组提交持久化、effectively-once 结算、房间级 WS 路由隔离、按 engine_seq 幂等防重复扣款；前瞻性：事件溯源真源模型、撮合引擎级恢复（快照+增量重放） |

## 4. 加分项（脱颖而出）

### 4.1 极致竞价氛围体验

- 领先「🎉 领先！」/ 被超越「⚡ 被超越！」情绪反馈，由服务端权威事件触发（不靠客户端猜）。
- 实时排行榜 + 我与最高价差距：快照读保证同一时刻一致视图（防「次数 10、价还是旧值」的 UI 撕裂）。
- 倒计时动画/出价音效；延长毫秒级同步重置。

### 4.2 高并发架构的硬核优化（**给评委的惊喜在这里**）

| 加分点（宣讲版原文） | v3 硬核兑现 |
|---|---|
| Redis 分层缓存、读写分离 | 决策态/幂等/**决策日志流**分层；围观读走副本/边缘短 TTL，**出价校验只走主**（防读从库旧价引发无效冲突） |
| 分布式锁解决出价幂等性，**绝不允许一笔出价扣两次钱** | 幂等键 + **fencing token + 条件更新 + 支付幂等键三层** = effectively-once，一拍品恰一次扣款 |
| WS 房间级路由隔离，单直播间 **1000+ 同时在线** | 房间级路由 + 合并广播；决策 p99≤50ms 支撑 1000 最后一秒爆发 |

**真正的「狠核」惊喜**：把单热点竞价当成**金融撮合引擎**来做——
单写者解并发、事件溯源解持久、组提交解吞吐、fencing+幂等解结算。
这套组合是 LMAX / 交易所 / 大厂秒杀的同源工业解，**用对了场景**，而非堆砌中间件。

## 5. 一句话「为什么我们能赢」（给评委的电梯陈述）

> 别人要么用 PG 行锁「对但慢」，要么用 Redis 预扣「快但错」。
> 我们识别出问题本质是**单热点强一致更新**，采用**单写者决策日志 + 组提交持久 + effectively-once 结算**：
> 决策在 Redis 单写者内 50ms 同步拍板且全序正确，持久化与结算在关键路径之外异步且诚实地追上，
> Redis 崩溃可由不可变日志亚秒级重建、且契约保证「已确认/已成交」永不丢错。
> **又快、又对、又能在故障下安全——这才是珠宝级高价值竞拍该有的工程。**
