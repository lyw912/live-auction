# Demo 编排与 3 分钟录制脚本（评委向）

> 日期：2026-06-07
> 目标：把“一堆散功能”串成**一个可信、看得懂、有结果**的业务故事，并产出可直接提交的《核心功能清单》《端到端流程》《3 分钟分镜脚本》。
> 前置阅读：`审查与评分报告`（为什么这么演）、`附录-行业调研汇编`（标杆怎么演 + 合规话术）。
> 关键前提：本项目能力其实很全且能跑；2026-06-07 后续 UI audit 已把演示数据、中文拍品、人读文案、PC/H5 Playwright 门禁收口。录前仍必须做 §1 的数据治理，因为真实库会随时间产生历史订单和过期状态。

---

## 0. 核心原则（先定调）

1. **不要展示全部功能，只讲一个完整故事。** 评委 3 分钟内要能回答：谁在用、各自想干嘛、哪些动作是真后端、产生了什么结果、技术深度在哪（被问到时）。
2. **一条主线**：`商家开拍 → 买家出价 → 实时被超越/榜单/延时 → 封顶落槌成交 → 买家结果/订单 + 商家复盘/证据`。
3. **砍掉稀释项**：福袋、PK/战队、答疑、满屏诊断、三窗口、纯脚本——这些放“附录材料”，不进主视频（理由见《审查报告》§5）。
4. **合规话术**：抖音内是**竞拍/竞价，不是拍卖**。全程用「**开拍 / 出一手 / 中拍 / 落槌成交**」，**不要**说「拍卖 / 开始拍卖 / 拍卖成功」；并在拍品信息处标「**支持 7 天无理由**」。（依据见《附录》§1.7）

## 1. 录制前置：数据治理（P0，不做就会“看起来坏了”）

> 初始审查时默认 `auc_live` 的 `end_at` 已过期、`item_title=NULL`，H5 会 fail-closed 显示「同步中·暂不提交出价」。当前 `p0smokeseed` 已扩展为清理主/副直播间演示残留并重建中文珠宝主拍品；录前仍要重跑，因为 `end_at` 和真实历史数据会随时间变化。

**最简治理（已验证有效，重置后 H5 立刻健康可出价，见 `shots/h5-06-live-clean.png`）：**

```bash
# 1) 基础设施在跑（已 healthy：postgres/redis/kafka/minio）
docker compose -f infra/docker-compose.yml ps

# 2) 后端在跑（:18080 readyz ok）
#    curl -s localhost:18080/readyz

# 3) 录前重置 demo 主/副直播间（清空历史演示残留，重建中文珠宝主拍品）
GOCACHE=/tmp/go-build-cache GOMODCACHE=/tmp/go-mod-cache GOPATH=/tmp/go-path go -C backend run ./cmd/p0smokeseed

# 4) 起前端（如未起）
pnpm dev:h5   # http://127.0.0.1:5276
pnpm dev:pc   # http://127.0.0.1:5277
```

**当前推荐：**
- 直接使用 seed 后的中文主拍品：`天然翡翠A货平安扣吊坠`，H5/PC/accept/live PC 已围绕它验证。
- 若现场用 PC「创建拍品和竞拍」新建拍品，价格规则已按 **¥ 元** 输入，不再按“分”填写。

> 录前自检：H5 进直播间应显示中文翡翠拍品、真实热度、`已连接`、`出一手 ¥...` 且按钮可点。PC 顶栏应是房间名 + 聚合健康灯（`引擎 ● 正常/降级/异常`），不应再展示 `待同步/最久 ms` 等原始指标。

## 2. 录制设置（两窗口左右分屏）

- **布局**：左 = 买家 H5（移动视口，建议 390×844 或浏览器移动模拟）；右 = 商家 PC 工作台（1440×900）。
- **为什么是“1 个真买家 H5 + 商家演示助手”而不是开 3 个 H5**：三窗口会让评委问“我在看谁”。**商家端「演示助手」模拟第二买家，但它调用的是真实后端出价接口、产生真实事件**，H5 通过正常实时链路收到更新——这比纯前端假状态可信得多，也比开一堆窗口清爽。
- **可选加分**：在“被超越”那一段，**真的再开一个 H5（第二个买家身份）手动出价一次**，作为“多用户真实并发”的铁证；其余竞争用演示助手加速。
- 录制规范：浏览器缩放 90–100%；关书签栏/侧栏；不开 DevTools；先讲意图再点击；全程一个诊断/证据画面即可；成片 ≤ 3 分 15 秒；**可加速**非关键操作但价格/倒计时/结果要看清。

**字幕（务必出现，防“作假”质疑）：**
> 左侧为买家 H5，右侧为商家工作台。为压缩录屏时长，右侧「演示助手」模拟另一位买家的竞争行为；该行为调用真实后端接口并产生真实竞拍事件，可在「出价记录 / 事件回放」中验证。

## 3. 三分钟分镜脚本（逐段：画面 / 操作 / 旁白 / 必拍 / 避免）

> 时间是目标值，可按实际节奏 ±5 秒。旁白用普通话，简短口语化。

### 0:00–0:15 这是什么
- 画面：双窗口同框；PC 在「竞拍」，H5 在直播间健康态。
- 旁白：“这是一套**直播竞拍**系统。商家在工作台控场，买家在手机出价，**价格、排名、延时、成交、订单、复盘全部由服务端驱动**。”
- 必拍：PC 标题/房间名（中文）、H5 直播台、一件中文拍品卡（当前价 + 倒计时）。
- 避免：诊断表、原始 ID、性能数字。

### 0:15–0:45 商家开拍（规则冻结）
- 画面：PC 聚焦「竞拍/拍品」。
- 操作：展示选中拍品与规则摘要（起拍 ¥100 / 加价 ¥50 / 封顶 ¥600 / 保证金 / 末段延时）→ 点「**开拍**」。
- 旁白：“开拍前，商家设定**起拍价、加价幅度、封顶价、保证金、末段延时**规则；**一旦开拍，规则即冻结**，保证买家信任。”
- 必拍：拍品名（中文）、当前价、倒计时、“规则已冻结”。
- 避免：从零填表（若时间紧，用已准备好的拍品，并口头说明“这是预置演示拍品”）。

### 0:45–1:20 买家出价（服务端确认，不乐观成功）
- 画面：H5 聚焦。
- 操作：点拍品卡 → 半屏「**拍品与规则**」快速带过（证书/品相/保证金/延时/误触保护）→ 出价一次（按钮印「**出价 ¥400**」）。
- 旁白：“买家先看**可核验的拍品信任信息**再出价。客户端**不会本地宣布成功**，而是**等服务端确认**才显示‘你已领先’。”
- 必拍：印着“下一口价”的出价按钮、等待确认→“你已领先 / 我的排名 #1”（`shots/h5-09-leading.png` 即此态）。
- 避免：问答、福袋、声音开关。

### 1:20–1:55 竞争与被超越（真实事件，无需刷新）
- 画面：左右分屏。
- 操作：PC 点「**第二买家超越**」（演示助手，出价=当前价+一口）→ H5 自动变“已被超越 / 需 ¥X 反超 / 榜单刷新”；（可选：真开第二个 H5 手动出价一次）→ 打开「**出价榜**」解释名次。
- 旁白：“为压缩时长，商家用**演示助手**模拟另一位买家——但它走**真实后端出价链路、产生真实事件**，买家端通过**实时推送**自动更新，**全程没有手动刷新**。”
- 必拍：PC 动作 → H5 被超越反应 → 榜单/名次变化。
- 避免：手动刷新 H5；把“演示助手”当普通功能（要点明）。

### 1:55–2:25 末段延时 + 封顶落槌成交
- 画面：左右分屏。
- 操作：PC「**窗口出价/延时**」触发末段延时（H5 显示“有人出价，延时 +10 秒”）→ PC「**封顶成交**」触发封顶/落槌。
- 旁白：“**末段出价按规则自动延时**，防最后一秒抢拍；达到**封顶价或终态条件**时，**服务端给出结果**，买家看到成交结局。”
- 必拍：延时文案/倒计时变化 → 落槌结果（`shots/h5-11-sold.png`：成交价、谁中拍、输家差额、查看订单入口）。
- 避免：把落槌当客户端倒计时归零（要强调以服务端结算为准）。

### 2:25–2:50 商家复盘与证据（反“作假”）
- 画面：PC 聚焦。
- 操作：点「**生成复盘**」展示复盘/高光卡（或短视频）→ 打开「**事件回放 / 出价记录**」几秒。
- 旁白：“成交后商家自动得到**复盘与高光素材**。若怀疑真假，**事件回放与出价记录**里有这场的**出价、成交、订单**真实落库记录。”
- 必拍：复盘/高光卡 + **一个**证据画面（事件回放或出价记录）。
- 避免：把所有诊断 Tab 扫一遍。

### 2:50–3:00 收尾
- 旁白：“三分钟里，这展示了完整闭环：**商家开拍、买家出价、实时竞争、规则延时、服务端成交、商家复盘**。底层是 **Redis 实时决策 + Kafka 决策日志/围栏 + PostgreSQL 结算真相**，断连/异常时**失败即关闭、可对账恢复**。”
- 画面：回到双窗口；可叠一张架构图静帧 2 秒。

## 4. 可直接提交的文案（按官方《成果演示 DEMO》栏目）

### 4.1 核心功能清单（5 条，按用户路径）
1. **商家开拍**：创建拍品、配置起拍价/加价幅度/封顶价/时长/末段延时/保证金，开拍后规则冻结。
2. **买家出价**：进直播间看可核验拍品信息与规则，出价后**等服务端确认**再显示领先，绝不乐观成功。
3. **实时竞争氛围**：榜单、倒计时、被超越提醒、末段自动延时、出价滚动——全部由服务端事件驱动。
4. **服务端成交**：封顶/终态由服务端结算，生成中拍结果、买家订单与（模拟）支付链路。
5. **复盘与可追溯**：成交后生成商家复盘/高光，事件回放与出价记录可证明出价、成交、订单真实落库。

### 4.2 端到端使用流程（6 句）
商家先在 PC 工作台准备拍品并设定竞拍规则，点击开拍后规则冻结。买家从 H5 进入直播间，查看商品图、可核验证书与竞拍规则后出价；页面等待服务端确认后才显示“你已领先”。商家用演示助手模拟另一位买家出价（走真实后端接口），买家端通过实时事件看到“被超越”和榜单变化，全程无需刷新。末段出价触发规则自动延时，达到封顶价时服务端给出落槌成交结果。成交后买家看到结果与订单入口，商家生成复盘与高光，并可在事件回放/出价记录中验证整条链路真实发生。底层以 Redis 实时决策、Kafka 决策日志/围栏、PostgreSQL 结算真相协同，断连或状态不可证明时失败即关闭并可对账恢复。

### 4.3 关键工程难点与解决方案（3 条，供“难点”栏）
1. **末秒高并发下的强一致出价**：Redis 原子实时决策 + Kafka 有序决策 WAL/围栏 + PostgreSQL 结算/审计真相；幂等保证“一笔出价不会扣两次钱”。
2. **WebSocket 不稳定下的可信状态**：服务端权威价/倒计时/赢家，客户端无乐观成功；断连/不可证明时 fail-closed，并以快照/对账恢复。
3. **可观测与故障兜底**：竞拍状态监控、对账、故障注入演练（PTS-1B：1000 末秒并发、出价决策 p99 ≤ 50ms 目标）。

### 4.4 项目亮点（3 条以内，供“亮点”栏）
1. **服务端权威 + 失败即关闭**：从不相信客户端时间/价格/赢家/成交，正确性优先（行业反面教材是“客户端假领先”，见《附录》§1.4）。
2. **可信竞拍体验**：可核验证书入口、保证金、末段延时防抢拍、匿名出价流——对齐 Whatnot/抖店并守住合规话术。
3. **可追溯**：事件回放/出价记录让“氛围不是假的”可被验证。

### 4.5 其他栏目快速提示
- **在线 Demo**：本地 `5276/5277`；若不便公开，用本视频替代，并附 README 启动步骤。
- **系统架构图**：用 `docs/current/architecture.md` 出一张“前端(H5/PC)→网关→Redis/Kafka/PG→监控”的图（《重构》文档给了结构）。
- **AI 能力说明**：解说生成/上架草稿/风控哨兵/复盘——写清模型/接口与在系统中的位置（对应 `/api/host/ai/*`）。
- **性能附录**：PTS-1B 证据链按 `docs/current/evidence-policy.md` 与 `tests/pts/MANIFEST.md` 附上，**不在主视频里念数字**。

## 5. 被评委追问时的应对（防守话术）

| 追问 | 应对 |
|---|---|
| “是不是脚本假装有人出价？” | “演示助手走真实 `/api/demo/auctions/{id}/competing-bid` 接口，产生真实事件与订单；这里打开**出价记录/事件回放**给您看落库记录。”（必要时现场再开一个 H5 真出价） |
| “断网了怎么办？” | “客户端无乐观成功，断连即显示‘状态确认中’并 fail-closed；恢复走快照/对账，不会假成交。” |
| “价格/赢家会不会被前端篡改？” | “价格、倒计时、赢家、成交全部服务端权威，前端只渲染服务端确认结果。” |
| “这是拍卖吗？合规？” | “这是**直播竞拍/网络竞价**，非牌照拍卖；拍品页标注**支持 7 天无理由**，证书提供可核验入口。” |
| “并发能力？” | “PTS-1B 目标 1000 末秒并发、出价决策 p99 ≤ 50ms，证据链见性能附录；本演示是功能演示，不替代压测证据。” |

- [ ] 字幕已写明“演示助手走真实后端”。
- [ ] 左 H5 / 右 PC 分屏，缩放 90–100%，无 DevTools/书签栏。
- [ ] 准备好**一张**证据画面（事件回放或出价记录）与**一张**架构图静帧。
