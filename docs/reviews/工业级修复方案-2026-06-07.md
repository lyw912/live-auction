## 0. 总原则与全局护栏（实现模型必须先读）

### 0.1 三条不可违反的设计原则
1. **复用既有"规范规则"，只改"在哪/何时执行"，绝不重算业务公式。** proxy/max-bid 的"赢家与成交价"解析已存在于 PG lane（`backend/internal/auction/max_bid_intent.go`，353 行）；fat-finger 阈值语义已存在于规则层（`rules.go` / `bid.go` 的 `ClassifyBidAmount` 与 `/bids/confirm` 流程）。**热引擎改造 = 把同一套规则搬到热路径执行（Go resolver 经同一条 Lua CAS 注入出价 / Redis 化的确认态），而不是另写一套公式。** 这同时消除评审里的"两条引擎规则不一致"(L7)。
2. **Lua 决策保持 O(1)，绝不在单条 EVAL 里跑级联循环。** 已联网核实：Redis Lua 脚本执行期**阻塞单线程**，"keep scripts short"。proxy 级联必须在 **Go resolver** 里完成，按 CrackingWalnuts 模式"经同一条快路径注入普通出价"，每次 EVAL 仍是一笔 O(1) 决策。
3. **fail-closed 不变。** 任何不确定（状态缺失/确认 token 失配/解析与现状冲突）一律拒绝或暂停，绝不伪造成功。

### 0.2 必须保持的既有不变量（每个改动都要有测试证明仍成立）
- 每拍品 `engine_seq` **无缝单调**；注入的 proxy 出价、确认落定都走同一 `engine_seq` 分配，不得制造缺口。
- **终态唯一**（SOLD/ENDED/CANCELLED once）；`request_hash` 幂等（同键同哈希 replay、同键异哈希 conflict）。
- **不泄露 client 真相**：proxy 隐藏最高价、确认中的待定额，**绝不**出现在任何 WS 事件/快照/排行榜 payload。
- outbox 有序可重放；对账器违例即暂停。

### 0.3 默认路径与兼容覆盖
- A1/A2 不保留 `BID_ENGINE_FAT_FINGER_HOT` / `BID_ENGINE_PROXY_HOT` 运行期开关；能力已经合入 Redis hot ledger 默认路径。
- 普通 `.env` / `.env.example` 不再暴露 `BID_ENGINE_MODE`。代码默认和 gateway 空配置归一化均为 Redis hot ledger；`postgres_lane` / `redis_guard` / `redis_aof` 不再作为当前运行档位。
- `loadSnapshot` 里的 `fat_finger_confirm` / `active_max_bid_intent → requires_postgres` pause 分类已删除。

### 0.4 验收总门（DoD，见 §9 细化）
旗舰 `redis_ledger + kafka_ack` 下：种子主拍品（含 fat_finger 且预置 proxy）**全程不暂停**跑到 SOLD；`go test ./...` 全绿（含新增测试）；对账器 green；用评审用过的"多出价者 + 隐藏最高价"脚本在旗舰模式跑通。

## 1. A1 — fat-finger 二次确认上热引擎（Redis 原生）

### 1.1 根因
`engine.go:1066-1116 loadSnapshot`：`fat_finger_threshold_cents IS NOT NULL → RequiresPostgres='fat_finger_confirm' → e.pause()` 并持久化 `engine_paused=true`。导致配了 fat-finger 的拍品在热引擎下一碰即持久暂停（评审 H1 现场翻车点）。

### 1.2 行业依据
LMAX/Event-Sourcing 的经典多步流程"下单→在内存挂起→等确认事件→落定"即二次确认的同构形态（单写者引擎天然支持，无需外部库）。确认态是一段**短时、按 (auction,user,client_bid_id) 键控的待定状态**，Redis 完全胜任。

### 1.3 语义（必须与 PG lane 完全一致）
- 判定口径**严格复用** PG lane 的 fat-finger 规则（跳价口径：`amount - current_price >= fat_finger_threshold_cents` 触发确认；以现有 `ClassifyBidAmount`/`rules.go` 为唯一真相，**不要在 Lua 里另写阈值常量**——把判定所需输入喂进 Lua，或在 Lua 里内联同一表达式并用 parity 测试锁死）。
- H5 既有 `confirm_required` UI 与 `/api/auctions/{id}/bids/confirm`（`router.go:150` `ConfirmBid`）**直接复用**，前端零改动。

### 1.4 数据与流程（Redis 原生）
- 首发出价命中 fat-finger 且未带有效 token：Lua 返回 `FAT_FINGER_CONFIRM_REQUIRED` + `confirm_token`；同一原子 EVAL 内写入待定键
  `bid_engine:{auctionID}:pending_confirm:{userID}:{clientBidID}` = `{amount, token, expires_at}`，`PEXPIRE` 30s。
  幂等：同 `clientBidID`+同 `amount` 必返回**同一** token（命中即复用）。
- 确认请求（带 `confirm_token` + 原 `clientBidID` + `amount`）走**第二个 Lua 入口** `confirmBid`：
  1. 校验待定键存在、token 匹配、未过期；否则拒（`CONFIRM_TOKEN_INVALID/EXPIRED`）。
  2. **以当前最新状态重新做常规决策**（重新校验：on-grid、≥当前最低价、ACTIVE、未超 cap、非自领先）——价格在确认间隔里可能已被他人推高。
  3. 任一校验失败 → 按对应原因拒（`BID_TOO_LOW`/`AUCTION_NOT_ACTIVE`/...），**不得**盲目接受过期语义的高额出价。
  4. 通过 → 删待定键，按常规"接受"路径落定（分配 `engine_seq`、写决策流、idem 记录，与普通出价完全相同）。

### 1.5 边界/并发/幂等
- 确认时拍品已终态 → 拒终态。
- token 过期 → 拒，要求重发（前端已有重试）。
- 确认重放（同 token 两次）：若该 `clientBidID` 已落定 → 命中既有 `request_hash` 幂等返回同结果；未落定 → 第二次确认走同一原子 EVAL，自然串行。
- 并发确认/并发出价：Lua 原子串行，无窗口。

### 1.6 测试矩阵（A1）
- 命中阈值→返回 token；非命中→直接接受（普通出价不受影响）。
- 阈值边界（`amount-current == threshold` 与 `== threshold-1`）。
- token：正常确认通过 / 过期拒 / 金额不符拒 / 错误 token 拒 / 重放幂等。
- 确认间隔内价格被他人推高 → 确认时按 `BID_TOO_LOW` 拒。
- 确认遇 cap → 落定即 SOLD。
- **parity**：同输入下热引擎确认结果 == PG lane `ConfirmBid` 结果。

## 2. A2 — proxy / max-bid 上热引擎（Go resolver，经同一条 CAS 注入）

### 2.1 根因
`loadSnapshot` 对 `active_max_bid_intent` 同样判定 `RequiresPostgres → pause`。

### 2.2 行业依据（已联网核实，写进方案以备拷打）
- eBay/Roth：proxy = 隐藏最高价；赢家=最高 max；**成交价 = 次高 max + 一个增量，封顶到赢家自身 max**；**平局取最早提交者**，以相等额全额成交；低于当前价的 max 视为无效/被即时超越。
- CrackingWalnuts（50K bids/s 同构架构）：proxy 由 `proxy-bid-resolver` 消费者**经同一条 API/CAS 路径**注入自动出价，"每笔出价行形状一致，只是发起者不同"，级联在"仅剩一个最高价在上方"时**终止**。
- Redis Lua 阻塞单线程 → 级联**必须**在 Go 里做，不入 EVAL。

### 2.3 唯一真相 = 复用 PG lane 的解析
**赢家/成交价的计算复用 `max_bid_intent.go` 既有解析函数**（它已实现 max-bid 语义）。本任务**新增的只是热路径载体**：
- 隐藏最高价的热态镜像（PG 仍为持久真相）：`max_bid_intents` 表已存在（迁移 `202605270001`）。热路径加 Redis：每拍品一个 ZSET `bid_engine:{A}:proxies`（member=userID, score=max_amount_cents）+ meta 哈希存 `created_seq`（平局用）；以及 `bid_engine:{A}:user_high`（userID→该用户最高已接受出价额，供"承诺额"计算）。
- **PUT/DELETE max-bid 时同步 PG + Redis**；要求 `max_amount_cents` 在网格上且 ≥ 当前最低价（与 PG lane 校验一致），否则拒。

### 2.4 Resolver（Go，收敛式反馈环；伪代码）
```
// 触发：每当一笔“被接受”的决策（人工或 proxy）改变 (current_price, winner) 后，
// 由已存在的“消费 Redis 决策流/Kafka 的 worker”调用：
func resolveProxies(A, respondingEngineSeq):
    st = readHotState(A)                       // P=current_price, W=winner, status, cap, increment, start
    if st.status != ACTIVE: return
    // commitment(u) = max(activeProxyMax(u)|0, userHigh(u)|0)；当前赢家若无 proxy，用其 userHigh 作承诺
    commit = buildCommitments(A)               // O(#proxies)，全部来自 Redis 镜像
    (winnerStar, priceStar) = RESOLVE(commit, P, W, increment, start, cap)
            // ↑ 直接调用/移植 max_bid_intent.go 的同一解析：
            //   winnerStar = 最高 commitment（平局取最早 created_seq）
            //   priceStar  = snapToGrid(次高 commitment + increment)，封顶 min(winnerStar.commit, cap)
            //   （次高若无 → start+increment 或维持 P，按 PG lane 同口径）
    if W == winnerStar and P == priceStar: return        // 已收敛，不注入
    cbid = det(A, winnerStar, respondingEngineSeq)        // 确定性幂等键，防重复注入
    placeBidThroughSameLuaCAS(A, winnerStar, priceStar, cbid, origin=PROXY)
    // 注入出价经同一原子 CAS：
    //  - 若期间被人工推高使 priceStar 不再合法 → Lua 常规拒绝；那笔人工出价的“被接受决策”会再次触发 resolveProxies → 重新收敛。
    //  - 若被接受 → winnerStar 成赢家 → 触发新一轮 resolveProxies（respondingEngineSeq 变 → 幂等键变）→ 直至 (W,P)==应然，终止。
```
- **直接跳到应然价（一跳），非逐增量爬**：步数 = O(不同承诺额层数) ≤ #proxies，绝非 O(价差/增量)。
- **on-grid**：因要求 max 在网格上、priceStar=次高(网格)+increment 并封顶到赢家 max(网格)，结果天然在网格上，满足现有 `(amount-base)%increment==0`。

### 2.5 边界/并发/幂等（逐条）
- 设 max 时已是赢家：不注入（除非他人 max 迫使）。
- max 低于当前最低价：PUT 时拒（与 PG lane 一致）。
- 两个相等 max：最早 `created_seq` 赢，成交价=相等额（全额），由 RESOLVE 平局规则保证。
- priceStar == cap：注入出价==cap → 现有 Lua `==cap→SOLD` 落锤。
- **隐藏额保密**：注入出价的 amount 是 priceStar（公开价），**绝不**把 max 写入任何事件/快照/排行榜。
- **幂等**：注入用确定性 `client_bid_id`（含 respondingEngineSeq）；resolver 重跑同一决策不重复注入；注入出价本身经 `request_hash` 幂等。
- **终止性证明**：应然 (winnerStar, priceStar) 是固定点；priceStar 单调不降且封顶 ≤ max(maxes) ≤ cap；每次注入严格趋近固定点 → 有限步收敛。
- 撤销 max（DELETE）：同步删 Redis+PG；下一次任何决策触发 resolver 自然重算（不会再代该用户出价）。

### 2.6 与防狙击(自动延时)的交互（决策点，写明）
- **建议：proxy 注入的自动出价不触发延时**（只有人工出价触发 `extend`）。理由：避免两个 proxy 在窗口内互顶导致延时被反复触发；人工触发的那一笔已延时，proxy 收敛是其后果。把该规则作为显式不变量并测试（双 proxy 窗口内互顶 → 延时次数不被 proxy 额外增加）。

### 2.7 测试矩阵（A2）
- 单 proxy 被人工超越→自动反超到"次高+增量"，不爬到 max。
- 双 proxy：高者赢，成交价=次高 max+增量（封顶到高者 max）；相等 max→最早者赢、全额。
- proxy 与人工交错；人工在 resolver 注入间隙插入 → 最终收敛正确。
- proxy 触 cap → SOLD，赢家=该 proxy。
- **seq 无缝**：注入出价不制造 `engine_seq` 缺口（对账器 green）。
- **幂等**：同一决策重复触发 resolver 只注入一次。
- **保密**：抓取所有 WS 事件/快照，断言不含任何 max 值。
- **parity**：同输入下热引擎最终 (winner, price) == PG lane max-bid 结果。
- 防狙击交互：双 proxy 窗口内互顶，延时次数符合 §2.6 规则。

## 3. M1 — 保证金一致性（默认热路径无视配置）

### 3.1 根因
`engine.go:3659-3678 createOrder` 硬编码 `deposit_cents = amountCents/10`，无视 `auction_rules.deposit_bps/deposit_floor_cents/deposit_cap_cents`；而 PG lane(`bid.go` `CalculateDeposit`) 与 scheduler(`scheduler.go:458 calculateDeposit`) 遵守配置并做 floor/cap 钳制。→ 同一拍品按不同结算路径保证金不同（评审 M1）。

### 3.2 修法
- 抽出**单一规范函数** `auction.CalculateDeposit(amountCents, depositBps, floorCents, capCents) int64`（删除 scheduler 的重复实现，全部改调它）。
- `createOrder` 增参 `depositBps, floorCents, capCents`，在结算事务内从 `auction_rules`（结算已 JOIN 拍品/规则上下文）取值并调规范函数；NULL 时用与 scheduler 一致的默认（`COALESCE(bps,1000)/floor(10000)/cap(100000000)` —— 把默认也收敛到规范函数内一处）。
- 不变量：给定 (auction, 结算赢家, 成交额)，**保证金在 Redis 引擎 / scheduler / PG lane 三条路径完全相同**。

### 3.3 测试
- 配置 `deposit_bps=1500` → 三条路径成交后 `orders.deposit_cents` 一致（=15% 钳制后）。
- floor/cap 边界（极小额触 floor、极大额触 cap）三路径一致。
- NULL 配置 → 默认值三路径一致。

## 4. H3 — 终态围栏（定时 SOLD 不围栏 Redis + 对账器漏 SOLD）

### 4.1 根因
- `scheduler.go:187-265 processEndAuction` 设 PG `SOLD`/建单，但**零 Redis 调用**（不 fence）。
- `engine.go:3953-4000 checkTerminalFenced` 的 `switch` 仅 `CANCELLED/ENDED`，**SOLD 落 default → 不围栏**。
- 叠加：延时先落 Redis、异步才到 PG 且不重排 `END_AUCTION`，scheduler 可能在"延时尚未结算到 PG"时按旧 `end_at` 定时成交 → 赢家/订单与引擎不一致（评审 H3）。

### 4.2 修法（三处，配合）
1. **对账器纳入 SOLD**：`checkTerminalFenced` 的 `case "CANCELLED","ENDED"` 增加 `"SOLD"`（PG 终态而 Redis 仍 ACTIVE → 围栏 Redis、打点、记违例）。
2. **scheduler 终态即围栏**：`processEndAuction` 写完 PG 终态后调用 `engine.FenceAuction(ctx, auctionID, "ENDED_SOLD"/"ENDED")`，错误要处理/打点（不可静默吞）。
3. **收敛后才定终态（关键，闭合 wrong-winner 缝）**：scheduler 定时成交**赢家前**，先验证收敛——
   - 先 `FenceAuction`（停止接新出价）；
   - 校验该拍品**无 Redis 待结算决策**、**Redis `end_at <= now`**、**Redis 当前价/赢家 == PG 已结算值**；
   - 不满足 → **不定终态**，重排作业稍后重试（fail-closed），而非按可能滞后的 PG 状态拍板。
4. **延时重排作业**：Redis 引擎延长 `end_at` 时，结算应同步把 `END_AUCTION` 作业 `run_at` 推到新 `end_at`（避免 scheduler 按旧 `end_at` 抢跑）。

### 4.3 测试
- 自然结束 SOLD 后 Redis 被围栏，post-SOLD 出价被拒终态（不再依赖 Lua `now>end_at` 兜底）。
- 对账器：构造 PG=SOLD 而 Redis=ACTIVE → 一次对账即围栏并记违例。
- **竞态**：末秒延时出价 + 结算滞后 + scheduler 触发 → 不产生第二赢家/不与引擎不一致（要么收敛后正确成交，要么 fail-closed 重排）。
- 延时后 `END_AUCTION` 作业 `run_at` 被推后。

## 5. M2 — Kafka "精确一次"的真相（注释为假 + rebuild 重放缝）

### 5.1 根因与定性（已联网核实，写明以备拷打）
- `kafka_ledger.go:98` / `engine.go:3030` 注释声称"idempotent producer / exactly-once"，但 **segmentio/kafka-go 高层 `Writer` 无幂等生产者**（issue #233 "Exactly once" 仍未实现；`RequireAll`+`MaxAttempts` 只是 ISR 确认 + 重试，属 at-least-once）。
- **真正的 exactly-once 业务效果由 PostgreSQL 唯一约束 + `engine_seq` CAS 实现**——这正是业界推荐的"**at-least-once + 幂等消费者 = 有效精确一次(effectively-once)**"模式。**架构本身是对的**，缺陷只是"注释说了谎"会误导维护者，以及 rebuild 重放缝。

### 5.2 修法（分三层，按需做）
1. **必做·改注释说真话**：把上述两处注释改为
   `// Kafka 生产者为 at-least-once（segmentio/kafka-go Writer 无幂等生产者）；exactly-once 业务效果由 PG 唯一约束 + engine_seq CAS 保证（effectively-once / 幂等消费者模式）。`
   并在 `docs/current/architecture.md` 的"Durability Layers"补一句"PG 是 exactly-once 边界，Kafka 是 at-least-once（按设计）"。
2. **必做·修 rebuild 重放缝**：`resumeRedisEngine` bump epoch 后 `writeRedisStateSnapshot` 删 relay 游标会导致旧 epoch 流条目被重新 append，单条 `settlePayload` 把 `EngineEpoch<dbEpoch` 当 `markSettlementFailed`+pause（`engine.go:3113-3122`），批处理却有干净的 `skipped_pre_rebuild` 分支（`engine.go:2348-2354`）。**二选一**：
   - resume 时对决策流 `XTRIM` 到重建后的 seq；或
   - 给 `settlePayload` 补与批处理同款"旧 epoch + seq≤db_seq ⇒ skip"分支。
   目的：resume 不再因重放旧 epoch 条目而**误把刚恢复的拍品再暂停**（fail-closed，但伤 RTO）。
3. **可选·防御纵深（非正确性必需，文档化）**：若要生产者侧也去重，把 ledger 生产者从 segmentio/kafka-go 换成 **twmb/franz-go**（feature-complete、KIP-185 幂等默认开、支持事务）。强调：**当前不缺这层**，effectively-once 已由 PG 保证；列为"若未来要 EOS 纵深"的演进项。

### 5.3 顺手清死代码
- 删 `isUnknownKafkaAppendFailure`（零调用，`engine.go:1274`）与只写不读的 `kafka_append_attempted`（`engine.go:172`），避免再次误导"曾有未知-append 处理"。

## 6. M3 — 订单越权（host 看到全系统订单）

### 6.1 根因
`bid.go:1385-1410 ListOrders`：`role != "host"` 才按 `winner_id` 过滤；host 角色**无任何房间/归属过滤 → 返回全系统订单**（多租户越权）。路由 `router.go:156` 仅 `requireHost`（鉴权），无归属。

### 6.2 修法
- host 分支按归属过滤：
  ```sql
  SELECT o.* FROM orders o
  JOIN auctions a ON a.id = o.auction_id
  JOIN rooms    r ON r.id = a.room_id
  WHERE r.host_id = $hostUserID
  ORDER BY o.created_at DESC
  ```
  （必要时加索引 `auctions(room_id)`、`rooms(host_id)`；多为已有。）
- **顺手排查同类越权**：`ListUserOrders`、各 `monitor_*` host 端点是否也缺房间/归属过滤；统一以 `requireHostOwns*` 口径收口。

### 6.3 测试
- host A 仅见其房间订单，**看不到** host B 房间的订单。
- 普通用户仅见自己中标订单（不回归）。

## 7. 实施顺序与灰度（实际落地）
1. **M1/M2/M3/H3** 先收口基础正确性：保证金规范函数、Kafka 语义诚实化、订单/终态围栏。

4. 保留 `postgres_lane` / `redis_guard` 的显式测试覆盖用于历史兼容和诊断，不作为降级底座宣传。

## 8. 给实现模型的硬性 DO / DON'T
- **DON'T** 在单条 Lua EVAL 里跑 proxy 级联循环（阻塞单线程）。**DO** Go resolver 注入 O(1) 出价。
- **DON'T** 另写 fat-finger 阈值/proxy 解析公式。**DO** 复用 `rules.go`/`max_bid_intent.go` 既有规则并加 parity 测试。
- **DON'T** 让任何 max/待确认额进入 WS 事件/快照/排行榜。**DO** 只广播公开价/赢家。
- **DON'T** 让注入出价/确认落定绕过 `engine_seq` 分配与 `request_hash` 幂等。**DO** 走与普通出价完全相同的接受路径。
- **DON'T** 为"修而修"加 Kafka 事务。**DO** 先把注释改成真话 + 修 rebuild 缝；franz-go 仅作可选纵深。
- **DON'T** 在无测试下翻开 A1/A2 开关或删 pause 分类。

## 9. 总验收矩阵（DoD）
- `cd backend && go test ./... -count=1` 全绿；新增测试覆盖 §1.6/§2.7/§3.3/§4.3/§5.4/§6.3。
- 既有对抗性测试不回归（并发封顶单 SOLD、三发一效、reconcile 围栏、stale-epoch 暂停、幂等 replay/conflict）。
- 旗舰 `redis_ledger + kafka_ack`：种子主拍品（fat_finger=on + 预置两个 proxy）→ 真实多出价者脚本 → **确认通过 / proxy 自动顶价 / 封顶成交 / 全程不暂停**；`orders.deposit_cents` 符合配置；终态后 Redis 被围栏；对账器 green。不得以 PG lane、redis_guard 或 redis_aof 作为提交后验收替代。
- 抓包断言：全链路 WS/快照**无 max 泄露**。
- `engine_seq` 在含 proxy 注入的场次仍**无缝**。
