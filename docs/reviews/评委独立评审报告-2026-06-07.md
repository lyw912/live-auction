## 0. 一句话结论（先给评委的票）

这是一个**工程成熟度远超竞赛平均水平、达到"真实字节基础架构小队产出"质感**的项目：Redis Lua 原子决策 + Kafka 决策 WAL/围栏 + PostgreSQL 结算真相 + 对账器 + outbox 有序投递 + 失败即关闭（fail-closed）+ 完整可观测性，外加打磨到位的双端前端与真实可跑的 AI 解说。**它几乎肯定进入决赛圈/领奖台。**

但在"无条件冠军"这条线上，我作为评委会就两点强烈追问，且这两点是我**亲手实跑发现、而非读文档得来**的：

1. **旗舰热引擎与产品旗舰功能不能并存**（致命级架构裂缝）：Redis 热引擎**不支持防手滑二次确认（fat-finger）与代理/最高出价（proxy/max-bid）**，遇到带这些规则的拍品会**直接 fail-closed 暂停**。而 Demo 主拍品恰恰配了 fat-finger，所以**默认旗舰模式下根本无法出价**——这正是本地 `.env` 退回 `postgres_lane` 的真实原因。换言之：**"1000 路最后一秒 < 50ms"只对"被裁剪掉旗舰功能的简化拍品"成立**。
2. **PTS-1B 性能证据不可在仓库内复现**（git-ignore），且自报数字是 **58ms（"60ms 包络"，非宣传的 ≤50ms）**，严格"零窗口同时 1000 路"那一版被自己记录为 **134ms（不达标）**。

正确性侧（不双扣款、唯一终态、幂等、围栏、对账、恢复）则**扎实且有对抗性测试背书**，我也在真实系统上跑通了完整资金闭环并验证了支付幂等。

**我的票：决赛圈/领奖台 = 强 YES；冠军 = 有条件 YES**——条件是要么补齐双引擎功能对等（或把性能宣称显式限定到"简化拍品档位"），要么交出可复现的 PTS-1B 证据。详见 §7。

## 3. 旗舰模式真实实跑：本次评审最关键的发现

我把后端切到**真实 `redis_ledger`+`kafka_ack`** 启动（健康、Redis/Kafka/PG 全 ok、reconcile 循环运行），对 Demo 主拍品 `auc_live` 下第一笔正常出价（¥400，仅 +¥50）：

```
ENGINE_PAUSED: "redis ledger engine paused: fat_finger_confirm requires PostgreSQL rule path"
```

随后**所有后续出价均返回 `auction engine is paused`**。根因（📄 `engine.go:1066-1116` `loadSnapshot`）：

```sql
CASE WHEN ar.fat_finger_threshold_cents IS NOT NULL THEN 'fat_finger_confirm'
     WHEN EXISTS(... max_bid_intents ... ACTIVE) THEN 'active_max_bid_intent'
     ELSE '' END
```
→ 一旦 `RequiresPostgres != ''`，调用 `e.pause(...)` 并**把 `engine_paused=true` 持久化进 PG**（`engine.go:1112-1129`）。

**结论（高危 H1）**：旗舰 Redis 引擎**结构性地不支持** fat-finger 与 proxy/max-bid——而这两者**都在 H5 里有完整 UI**。任何配了这些规则的拍品在旗舰模式下"一碰即暂停且持久暂停"。Demo 主拍品正好配了 fat-finger，因此**默认旗舰模式下完全不可出价**——这才是 `.env` 退回 `postgres_lane` 的真实原因。

为验证旗舰**正常路径**确实可用，我新建了一个**不带 fat-finger 的拍品**重跑：引擎正常给出 `ENGINE_*` 决策（fail-closed 行为本身正确：缺 ACL 预热键时 `engine.go:680-681` 返回 ACL_FORBIDDEN，是安全的关闭而非伪成功）。配合已通过的 `redisengine` 集成测试套件（384s、真实基础设施、覆盖并发封顶/幂等/结算/恢复），旗舰引擎对"简化拍品"是真实可用且正确的。

**这意味着**：宣传的"1000 路 < 50ms"成立的前提，是**关闭了 fat-finger/proxy 的简化拍品**；而产品旗舰体验跑在被文档判定"达不到性能目标"的 PG lane 上。这是评委最该追问的一刀。

## 5. 问题清单（按严重度排序，含 file:line）

### 高危（冠军评定的关键追问）

- **H1｜双引擎功能不对等（实跑发现）**：Redis 旗舰引擎不支持 fat-finger / proxy-max-bid，遇到即持久 fail-closed 暂停（`engine.go:1079-1116`）。性能宣称只对简化拍品成立；产品旗舰功能只能跑 PG lane。**这是全报告最深的发现。**
- **H2｜PTS-1B 性能证据不可复现 + 数字打折**：⚠️ `s1` 原始件被 `.gitignore`，仓库内只committed两份 `S3`(扇出，非PTS-1B)控制台导出；自报 `UIPAX7JG` p99=58ms（"60ms 包络"，非 ≤50ms），严格零窗口同时 1000 路 `TGLBX7GG`=134ms（不达标，文档诚实保留）。正确性有测试背书，**性能为自证**。
- **H3｜定时自然结束 SOLD 不围栏 Redis，且对账器漏掉 SOLD**：`scheduler.go:187-265` 设 PG SOLD/建单但**零 Redis 调用**；`checkTerminalFenced`（`engine.go:3953-4000`）`switch` 只处理 `CANCELLED/ENDED`，**SOLD 落入 default 直接返回**。叠加"延时先落 Redis、异步才到 PG 且不重排 END_AUCTION 作业"，存在**赢家/订单与引擎不一致**的时序缝（对账器为部分兜底）。**在默认 redis_ledger 模式下此缝是活的。**

### 中危

- **M1｜保证金硬编码 `amountCents/10`**：默认 Redis 结算路径 `createOrder`（`engine.go:3669`）**无视配置的 `deposit_bps/floor/cap`**（PG lane 与 scheduler 用 `calculateDeposit` 遵守）。同一拍品按不同结算路径保证金不同；当商家配置非 10% 时旗舰路径仍收 10%。**资金相关，且位于默认路径，严重度上调。**
- **M2｜"幂等 Kafka 生产者"注释为假**（🌐 已证）：`kafka_ledger.go:98`/`engine.go:3030` 注释声称幂等，但 segmentio/kafka-go 高层 `Writer` 无幂等生产者语义（at-least-once）。真正 exactly-once 靠 **PG 唯一约束**。误导维护者，且 rebuild 路径"依赖该假保证"重置 relay 游标→可能**重放旧 epoch 流→误触再暂停**（仍 fail-closed，伤 RTO）。
- **M3｜订单越权**：`ListOrders`（`bid.go:1385-1410`）host 角色**无房间/归属过滤，返回全系统订单**。多租户下泄露其他商家订单。
- **M4｜排行榜 delta 有损**：单 worker（`server.go:79`）+ 满即丢（`leaderboard.go:78-82`）。"排名一致"只是**最终一致**（价格/赢家仍由有序事件流保证正确，客户端不回退）。
- **M5｜实时扇出仅单机**：`outboxrelay` 无 publisher，无 Redis pub/sub / NATS 跨节点总线。多实例下其他实例客户端只能靠重连/快照拿到更新。1000+ 为单机 ~3000 WS 实测、10000 未证（文档诚实声明）。
- **M6｜HEAD 有两套测试失败**：`internal/invariant`（10 个，清理期 FK——`ai_generation_jobs` 缺 `ON DELETE CASCADE`，AI 迁移引入）；`internal/realtime` 一个 WS 恢复用例（`event_type=snapshot` want `bid_accepted`）。属测试维护债，但"HEAD 不全绿"是成熟度红旗。

### 低危/打磨

- **L1**：图片上传无大小/类型校验（前后端皆无，`auction_handlers.go:248`）。
- **L2**：限流准入 Redis 出错时 fail-OPEN（`bid_admission.go:212-215`）——仅限流器，资金安全不受影响。
- **L3**：H5 与 PC **终态拍品仍显示倒计时/"下一口 ¥X"**（成交后应停）。
- **L4**：🌐 `nhooyr.io/websocket` 已 Deprecated，应迁到 `github.com/coder/websocket`（仅 import 路径，无 API 破坏）。
- **L5**：Grafana 死面板（`auction_bid_kafka_append_fail_total` 从不产出）；OTel 默认关闭（`OTEL_TRACES_ENABLED=false`）；漂移/不变量检查仅 CLI、非常驻扫描。
- **L6**：死代码 `isUnknownKafkaAppendFailure`（零调用）、`kafka_append_attempted`（只写不读）。
- **L7**：自动延时公式两引擎不一致——Redis `old_end+by`、PG `now+by`（`rules.go:126`），相同输入产生不同结束时间/可能不同赢家。
- **L8**：PG lane `createOrderForSoldAuction` 缺 `ON CONFLICT`，竞争下抛裸唯一冲突（500）而非优雅 no-op。
- **L9**：测试库污染（数千残留拍品/房间、~53min outbox 积压）——正式 Demo 前需 `p0smokeseed` 重置/清库。

## 6. 多视角交叉评语

- **架构师**：少见的"敢做对的难事"——把热决策从 PG 热行迁到 Redis Lua、用 Kafka 做有序 WAL/围栏、PG 守结算真相、对账器+epoch 围栏防脑裂。分层耐久性（ENGINE_DURABLE→KAFKA_ACKED→SETTLED→ORDER）与响应契约设计是工业级。**最大遗憾是 H1：两条引擎没做到功能对等，旗舰只能跑"阉割版"拍品。**
- **资深后端**：正确性纪律极好（原子决策、唯一终态三层、幂等 replay vs conflict、处处 fail-closed）。但 M1 保证金硬编码、M2 假幂等注释、H3 SOLD 不围栏，都是"细节里的魔鬼"，在真实资金系统会被 code review 拦下。
- **测试运维**：对抗性测试（三发一效、并发封顶单 SOLD、stale-epoch 暂停、relay 队首不跳）质量很高；Toxiproxy 8 场景、k6 全套。但 **HEAD 两套测试红**、PTS 原始证据不在仓库、OTel 默认关、漂移检查非常驻，是上线前必须清的。
- **前端**：双端打磨到位，抖音质感，状态语义诚实（无乐观成功、终态拉快照核对）。扣分在终态倒计时/下一口残留（L3）与图片上传无校验（L1）。
- **产品经理**：买家旅程完整且有情绪曲线（领先/被超越/成交+AI 解说），商家控场+诊断强。但"默认旗舰跑不动主拍品、要退 PG lane 才能演全功能"是 Demo 叙事的硬伤；订单越权（M3）在多商家场景是合规问题。

## 8. 可落地的优化清单（按性价比排序）

**P0（影响冠军评定，优先做）**
1. **H1 双引擎对等**：要么在 Lua 引擎内实现 fat-finger 二次确认（confirm token 走 Redis 状态机）、proxy/max-bid 的"按阶梯代出价"原子化；要么在产品/材料中明确"高级规则拍品走 PG lane、热引擎走简化档位"，并让 Demo 主拍品在旗舰模式可跑（去掉 fat-finger 或提供旗舰版拍品）。
2. **H2 证据可复现**：把一次干净的 PTS-1B 旗舰跑（含 SHA/JMX/CSV/metrics/verifier/durability 分布）以可复现形式提交；严格"零窗口同时 1000 路"若仍 134ms，则把性能宣称改为"釜底窗口 p99 58ms（kafka_ack）/23ms（redis_aof）"并标注窗口定义。
3. **H3 终态围栏**：scheduler 自然结束 SOLD 后 `FenceAuction`；`checkTerminalFenced` 的 `switch` 补 `SOLD`；结算推进 `end_at` 时重排 `END_AUCTION` 作业。

**P1（资金/正确性/安全）**
4. **M1**：`createOrder` 改用 `CalculateDeposit(amount, bps, floor, cap)`，与 PG lane/scheduler 统一；合并重复的 `CalculateDeposit`/`calculateDeposit`。
5. **M2**：修正"幂等生产者"注释为"PG 为 exactly-once 边界、Kafka 为 at-least-once"；rebuild 时对决策流 `XTRIM` 到重建 seq，或给 `settlePayload` 补"旧 epoch + seq≤db_seq ⇒ skip"分支，避免误触再暂停。
6. **M3**：`ListOrders` host 分支按房间归属过滤（`JOIN rooms r ON r.host_id=$user`）。
7. **M6**：`ai_generation_jobs.auction_id` 加 `ON DELETE CASCADE` 或修清理顺序；修复 realtime 快照-事件用例；让"unit"测试在无基础设施时 `t.Skip` 而非 `t.Fatalf`。

**P2（体验/运维/规范）**
8. **M4/M5**：排行榜 delta 多 worker + 背压可视化；规划跨节点扇出总线（Redis 分片 pub/sub 或 NATS），把"单机 ~3000 WS"升级为水平扩展。
9. **L1**：上传预签名限制 `Content-Type` + 大小，或落库后异步校验。
10. **L3**：终态隐藏倒计时/"下一口"。**L4**：迁 `coder/websocket`。**L5**：删死面板、默认开 OTel 采样、对账/不变量做常驻扫描+告警。**L7**：统一延时公式。**L9**：Demo 前清库重置。

## 9. 必须给予的肯定（避免只挑刺）

- **不双扣款**：✅ 实跑验证支付幂等 + 📄 `orders.auction_id UNIQUE`/`payment_events UNIQUE`/seq-CAS 三重保障 + 三发一效测试。这是课题的硬指标，达成且有背书。
- **失败即关闭**：未发现任何在 Redis/Kafka 写失败时伪造 `ENGINE_ACCEPTED` 的路径；旗舰实跑中缺状态即暂停/对账，绝不伪成功。
- **诚实**：文档主动披露 58ms≠50ms、单机扇出、~3000 而非 10000 WS、保留 134ms 失败诊断。**这种克制在竞赛里是稀有的成熟信号。**
- **AI 不在热路径**：`maybeCreateAutoCommentary` 仅入队、独立 worker 消费，引擎/拍卖包不 import AI。这是 SRE 最关心的隔离，做对了。
- **真实可跑的 AI 解说 + 多模态选品**：是同类方案少见的差异化亮点。
