# 统一"快引擎 + 富功能"——行业架构调研与改造方案

> 2026-06-07 · 回应"双引擎功能不对等（fat-finger / proxy-max-bid 在 redis_ledger 下被 fail-closed 暂停）"的追问。
> 结论先行：**这是实现方式造成的伪两难，不是架构定律。** 真实工业界（eBay、交易所撮合、大厂系统设计参考）都在**同一条快路径上同时支持**原子决策 + 代理出价 + 防狙击 + 精确一次结算。本项目其实已经拥有 90% 的零件，缺的是把"复杂规则 = 退回 PG = 暂停"的过保守判定，换成行业标准的"复杂规则 = 经同一条快路径回灌的另一种出价来源"。

---

## 1. 本项目为什么会撞墙（根因复盘）

`engine.go:1066-1116 loadSnapshot` 把规则分类成：

```sql
CASE WHEN ar.fat_finger_threshold_cents IS NOT NULL THEN 'fat_finger_confirm'
     WHEN EXISTS(... max_bid_intents ACTIVE)        THEN 'active_max_bid_intent'
     ELSE '' END
```

只要 `RequiresPostgres != ''` → `e.pause()` 持久化 `engine_paused=true`。本质问题：**把"需要跨多次调用的状态（确认）/跨多个出价者的级联（代理）"等同于"热引擎做不了 → 整场暂停"**。

但 Lua 决策脚本"只能表达一次 O(1) 决策"是 Lua 的限制，**不是热路径的限制**。证据：同一个引擎**已经能做"非 O(1)"的事**——防狙击延时就是一次决策里同时改价、改赢家、改 `end_at`、改 `extend_count`（`engine.go:309-321`）。既然延时能在热路径原子完成，代理/确认同样可以，只是要换个"摆放位置"。

## 2. 反证：行业标杆把这两者放在一起跑（proof by existence）

**CrackingWalnuts《System Design: Online Auction》**（50K bids/sec、1M watcher、p99<200ms）——架构与本项目几乎 1:1（Valkey/Redis CAS 决定谁赢 + Kafka 按 auction 分区 + Postgres fencing token 结算 + 反狙击 + 精确一次），而它的 Feature 清单**同时**包含：English/Dutch/Sealed-bid、**Proxy(auto) bidding**、**Anti-sniping**、**Effectively-once**。它对代理的实现一句话点破：

> Proxy bid cascade：一笔出价被接受后，`proxy-bid-resolver` 消费者读取该拍品的 `proxy_bids`，若他人的隐藏最高价高于新价，就**以其名义、经同一条 API 路径**提交 `current_price + min_increment` 的下一口；级联在"仅剩一个最高价高于当前价"时终止。
> **"从出价处理器的视角，每一笔出价行形状都一样，origin mode 只决定是谁发起的。"** manual / proxy / dutch_accept 走**同一个 Kafka topic、同一个 CAS 脚本、同一组 Postgres 写**。

**eBay 代理出价**（Stanford/Roth 论文、Gixen）：你提交隐藏最高价；系统**按最小加价梯度替你自动出价**，价格上抬到"超过次高最高价"为止（或被他人超过你的最高价）。赢家以"次高最高价 + 一个增量"成交——这是一个**有界、确定、必然终止**的解析（类二价/Vickrey），**绝非无限级联**，因此可以原子完成。

**LMAX 架构**（Martin Fowler）：单线程内存业务处理器 600 万 TPS，**Event Sourcing**——状态完全由输入事件流重放得到，输入先落 journal（durable）再处理。其经典多步流程：下单→发出"待校验"事件→**订单留在内存中等待"已校验"事件**→再确认。**这正是 fat-finger 二次确认的同构形态**（在内存里挂起一个"待确认"状态，等确认事件到达再落定），单写者引擎天然支持。

**交易所撮合 / Akka Cluster Sharding / Orleans / pyemma 拍卖系统设计**：共识是"**对某个实体（一只股票 / 一场拍卖）的所有请求都路由到唯一的有状态单写者**"，状态在内存、按 key 分区、用 WAL+snapshot 或重放恢复。单写者内可跑**任意**业务逻辑且仍是 sub-ms。

> 一句话：**真实工业界用"单写者 + 内存状态 + 持久输入日志"来同时拿到快与富**；代理/确认要么作为"经同一条快路径回灌的另一种出价"，要么作为"单写者状态机里的一段普通逻辑"。**没有人为此把拍卖整场暂停。**

## 3. 三种可行架构（按改造成本从小到大）

### 方案 A（最小改动，最贴合现有代码）：富功能 = 喂给同一条快路径的"出价来源"
- **代理/最高出价**：新增 `proxy-bid-resolver` worker。它**消费本项目已有的 Kafka 决策流**（每笔 ACCEPTED 决策已在流里），读取该拍品 ACTIVE 的 `max_bid_intents`，若有人隐藏最高价 > 新当前价，就**以其名义经同一个 `PlaceBid`/同一个 Lua CAS** 注入 `current+increment` 的自动出价；级联有界、按"仅剩一个最高价在上方"终止。秘密最高价存 Redis sorted set（+ PG 持久）。**删掉 `active_max_bid_intent → pause` 判定。**
- **fat-finger 二次确认**：本项目 PG lane **已有** `/api/auctions/{id}/bids/confirm`（`router.go:150` ConfirmBid）。把"待确认"状态从 PG 搬到 Redis：首单若跳价≥阈值，Lua 返回 `CONFIRM_REQUIRED + token`，把 `pending_confirm:{auction}:{user}:{amount}` 写入 Redis（短 TTL）；确认请求带 token 走第二个 Lua 入口落定。**删掉 `fat_finger_threshold IS NOT NULL → pause` 判定。**
- 收益：**几乎不动架构**，复用现有 Kafka 流/Lua/PG/对账；让旗舰引擎直接支持 Demo 主拍品。代价：resolver 注入的自动出价要计入幂等与 seq（沿用现有 `engine_seq`/请求哈希即可）。

### 方案 B（中期，最干净）：把"决策单元"从 Lua 脚本升级为"每拍品单写者状态机"
- 每场拍卖 = 一个**单写者 owner**（Go goroutine/actor 或"按 auction_id 分区、每分区单消费者"），在内存持有拍品状态，串行处理该拍品事件流，**输入日志仍是现有 Kafka WAL**（已具备），Redis 退为读/广播投影，PG 仍为结算真相。
- owner 内可原子跑**任意**逻辑：确认挂起、代理级联、Dutch 降价、保留价、反狙击……都不再受"单条 Lua EVAL"表达力限制，且仍 sub-ms（内存单写者）。
- 这是 **LMAX/Actor 的标准形态**，且对本项目是**演进而非重写**：你已经有 Kafka 有序日志 + 单线程决策思想 + PG 投影 + 对账/重放。补的是"把 Lua 换成可表达多步逻辑的内存状态机 + 每拍品单写者归属（分区租约你也已经有：outbox 16 分片 + relay 租约）"。

### 方案 C（规模化）：按 auction_id 分区的有状态消费集群
- Kafka 分区键 = auction_id；每分区唯一消费者持有该分区内所有拍品的内存撮合状态；passivation（空闲卸载）+ 重放恢复。即交易所"按 symbol 分区撮合"的拍卖版，天然水平扩展，顺带解决"实时扇出仅单机"（中危 M5）。

## 4. 为什么团队的直觉"对了一半"

团队**正确**地拒绝把代理级联/确认硬塞进单条原子 Lua EVAL——那确实会让脚本变脏、级联难以表达。但**错误**地由此得出"所以整场退回 PG 并暂停"。行业的正确推论是：

> **"所以把复杂逻辑拆成'经同一条快路径回灌的普通出价'(方案A) 或 '单写者状态机里的一段逻辑'(方案B)，而不是离开快路径。"**

原子决策保持 O(1) 纯净，富功能作为**反馈环 / 状态机逻辑**叠加——这正是 eBay/CrackingWalnuts/LMAX 的共同选择。

## 6. 方案选型决策（A/B/C 五维对比，作为拓展性思考）

> 结论：**A/B/C 不是必须逐级攀登的阶梯，而是三个不同层面的选择。** 只有 A 直接闭合 H1（被扣分项）；B/C 解决的是单机 Demo 看不到、课题也未要求的"引擎通用性 / 水平扩展"。竞赛阶段选 A（必要时先做 Option 0 兜底），B/C 推迟到"做成真实产品"再说。

| 维度 | **Option 0** 文档分档 + Demo 拍品改 plain | **A** 同路径（proxy resolver + Redis 化确认） | **B** 每拍品单写者状态机 | **C** 分区有状态集群 |
|---|---|---|---|---|
| 效果(评分/H1) | 中：消除"旗舰一出价即翻车"+误导宣称，但未达功能对等 | **高：完全闭合 H1**，可正当宣称"快+富同引擎" | 竞赛低增量(demo 无差别)；产品高 | 竞赛≈0(单机不可体现) |
| 难度 | 极低 | 中（确认易；proxy 中） | 高（换决策基座） | 很高（分布式归属/再平衡） |
| 风险(对既有正确性) | 极低 | **低-中且可控**（核心 CAS 不变；proxy 级联/幂等需护栏） | **高**（改写"已证正确性"皇冠资产，可能回归已通过套件） | 很高，且多数失败模式本机不可复现 |
| 工作量 | ~10 分钟 | 中（数天：小改 + ~12–15 针对性测试） | 大（数周：重写 + 重证全部不变量 + 生命周期测试） | 很大 |
| 不确定性 | 极低 | 低（模式有文档佐证、零件已具备） | 高（归属交接/恢复等价性待证） | 很高（大量本机不可验 → 再造"未验证宣称"） |

**为什么不必一个个来**：A 独立于 B/C，且 A 就足以闭合 H1。B 仅在"Lua + resolver 开始嫌挤、要做长期产品"时才需要；C 仅在"真要多节点水平扩展 + 跨节点扇出"时才需要（课题明确多 Redis/Kafka 缺失不扣分 → 竞赛边际价值≈0）。

**"只要实现就行吗？"——不行**：本项目评分护城河正是"可证明的正确性"。资金/热路径改动若无测试，等于自降质量标准（评委会查 tests/不变量），且 proxy 级联不终止 / 注入出价造成 seq 缺口 / 确认 token 重放等 subtle bug 一旦现场翻车，比"诚实暂停"更糟。但 A 的测试范围是**有界的、小的**（~12–15 个，沿用现有 `redisengine` 集成测试风格）。

**"B/C 要不要补很多测试？"——要，且很多，这本身就是不选它们的理由**：B 强制在新基座上**重证全部旧不变量**（并发封顶仅一 SOLD、幂等 replay/conflict、终态唯一、recovery/rebuild、seq 无缝、fail-closed）+ 新增状态机生命周期测试（passivation/rehydrate、单写者归属交接、多步中途崩溃）。C 还引入大量分布式测试（分区归属、再平衡、脑裂、跨节点扇出），其中很多**单机根本跑不出来 → 永远停在"未验证"**，反把"宣称不可复现"问题再造一遍。"本机测试没关系"救不了你——问题不在跑测试的成本，在**待重证面的体量**与**本机不可验证的面**。
