# 8 分钟提问追问与拷打 · 备战手册

> 模拟 5 位评委视角，每位 2-3 个必问 + 追杀链。**原则：能指到代码就指到代码，不会的直说。**

## 评委 A：架构师（10y+ TikTok 基础架构）

### Q1：为什么热路径不是 PG 行锁？

> 1000 人最后一秒竞争同一拍品行，行锁串行化。PG 的行锁在高并发写场景下，每个事务等前一个释放锁，p99 会飙到几百毫秒甚至秒级。Redis 单线程+Lua 原子脚本天然串行化，但没有锁等待开销——一段 Lua 一次 RTT 就是一个完整决策。PG 退居结算真相，由幂等消费者去重。

**追杀：PG 加连接池+短事务+乐观锁呢？**

> 乐观锁（版本号 CAS）在高争用时大量失败重试，1000 并发失败率极高，实际吞吐更差。短事务+连接池只降低等待时间，但同一行的更新仍然串行。而且 PG 连接数有限（几百），1000 并发直连 PG 不现实。Redis 没这些问题——单线程执行 Lua，每个决策微秒级。

**追杀：Redis 挂了你的"结算真相"也没了？**

> Redis 不是真相，PG 才是。Redis 丢了：暂停拍品→RECONCILING→从 Kafka 高水位+PG 结算态重建 Redis→校验 epoch/seq/价/胜者/终态→通过才恢复。代码在 `engine.go:3543-3855`，`rebuildRedisFromCheckpoint`/`recoverPendingDecisions`/`writeRedisStateSnapshot`。恢复期用户看到"恢复中"，禁用出价，不给假成功。

### Q2：Kafka 是不是过度设计？brief 只要求 demo。

> 直接承认 brief 只要求 demo。但 brief 自己提出了三个挑战：毫秒级同步 + 零漏洞规则 + 高并发。要同时满足这三个，决策必须有有序、可重放、可对账、可 fail-closed 的持久 WAL。Kafka 承担的就是这个角色：决策 WAL + 故障证据 + 结算重放源。不是为简历堆中间件。

> 用 Reconciler 和混沌测试证明：Redis FLUSHALL 后，从 Kafka 重建→校验→恢复→正确性门禁全绿。去掉 Kafka，这条路径断了。

**追杀：engine.go 5000 行单文件怎么说？**

> 坦白：这是技术债。Engine + Lua + Worker + Relay + 重建都在一个文件里，可维护性差。应该拆成 lua/engine/worker/relay/recovery 几个文件。不改行为，纯代码组织。时间原因没做。

### Q3：为什么不用成熟的分布式锁（Redlock/etcd）？

> Redlock 解决的是"多进程互斥"，我的场景是"单热点高频决策"。Redlock 每次加锁/解锁需要多次 RTT + 多 Redis 实例协调，延迟远高于单次 Lua 执行。而且 Redis Lua 天然保证原子性——脚本内的所有操作不会被其他命令打断。不需要外部锁。

## 评委 B：资深后端开发（10y+ 交易系统）

### Q1：幂等出价怎么实现的？跨用户重放怎么防？

> 三层防护：
> 1. `Idempotency-Key` HTTP 头必须等于 `client_bid_id`（`engine.go:placeBidWithSource:23`）
> 2. `requestHash = hash(auctionID, userID, clientBidID, amount)`——含 userID 和 amount
> 3. Lua 脚本内检查：同键同哈希→回放旧结果；同键异哈希→`IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST` 拒绝
>
> 所以：用户 A 的 client_bid_id 被用户 B 拿去重放→哈希不符（userID 不同）→拒绝。用户 A 自己拿同 client_bid_id 偷改金额→哈希不符（amount 不同）→拒绝。PG 端还有 `bids UNIQUE(auction_id, user_id, client_bid_id)` 兜底。

### Q2：exactly-once 怎么保证的？

> 不保证 exactly-once——明确说。`segmentio/kafka-go` 没有实现幂等 producer（KIP-185）。我们是 **at-least-once WAL + 幂等消费者**：
> - Kafka 可能重复投递同一条消息
> - PG 结算端用唯一约束 + engine_seq CAS 去重：重复投递→唯一约束冲突→跳过
> - 所以 PG 是 exactly-once 边界
> - 这是业界标准做法（Confluent 文档也这么说）

**追杀：Go 的 ClassifyBidAmount 和 Lua 的规则逻辑是两套实现，怎么保证一致？**

> 坦白：目前没有跨实现一致性测试。Go 的 `ClassifyBidAmount`（`rules.go`）和 Lua 内的规则逻辑是各自实现的。核心规则分类（太低/网格/封顶/误触）两者等价，但反狙击延时公式有一处实质背离：Go 用 `now+extendBy`（出价锚定），Lua 用 `end_at+extend_by`（end 锚定）。线上以 Lua 为准，自洽。Go 版本目前只被 PG legacy 测试路径和 `validateMaxBidIntentAmount`（活路径）引用。应该加一组 parity test 共享测试向量。

### Q3：engine_seq 拒绝也消耗序号，有什么意义？

> 关键在于对账。如果拒绝不消耗序号，你只能证明"接受的决策是连续的"，但无法证明"没有决策被悄悄吃掉"。拒绝也消耗→序号 1..N 完整无空洞→校验器可以断言：系统做了 N 个决策，每一个都在 PG 有记录，没有丢失也没有幽灵决策。

> 缺点：自我领先拒绝也消耗序号，领先者狂点会产生一串 REJECTED_SELF_LEADING 的持久决策——正确但浪费。可以在网关侧做轻量短路。

## 评委 C：运维/测试工程师（10y+ SRE）

### Q1：S1 的 p99 ≈ 23ms 这个数怎么来的？

> 来自 PTS（阿里云性能测试服务）S1 final-second-contention 场景：1000 VU 在最后 500ms 窗口内各出 1 次价。PTS 的 JMeter 采样器记录每个 HTTP 请求的端到端延迟（从发出到收到完整响应），聚合 p99。S1 中包含接受和拒绝两种，都计入采样——因为拒绝也是一个完整决策。

**追杀：这个 23ms 能复现吗？环境是什么？**

> 坦白：需要重跑。S1 当时跑在阿里云 ECS 上（云服务器+PTS 引擎），网络条件和机器配置与本地 Docker 不同。本地 Docker 因为 Redis/Kafka/PG 都在同一台机器，延迟更低但不代表生产。严格来说，这个数字是"方法论可信但需在目标环境重跑确认"。

### Q2：35 条门禁具体校验什么？举个例子。

> 以 `auction_winner_matches_highest_accepted` 为例：SQL 查 `SELECT MAX(amount_cents) FROM bids WHERE auction_id=? AND engine_decision='ENGINE_ACCEPTED'`，与 `auctions.current_price_cents/current_winner_id` 比对。如果不一致→P0 FAIL。

> 另一个：`engine_seq_complete`。用 `generate_series(1, max_seq)` 生成期望序列，与 `redis_engine_settlements.engine_seq` 比对，must have min=1, max=total, actual_count=total, missing=0。缺一个就 FAIL。

**追杀：没有跑 RF=3 多副本怎么保证 Kafka 不丢？**

> 坦白：当前是单 broker、RF=1。生产环境应该是 RF=3 + minISR=2。架构已预留（配置项可调），但成本受限没有跑多 broker 的压测。目前的正确性证据是单节点级别的——证明的是"链路逻辑正确"而非"分布式容灾"。

### Q3：RTO 是多少？

> 坦白：未量化。重建/恢复的代码存在且真实可执行（`rebuildRedisFromCheckpoint`），但目前只做了二元 pass/fail 测试（能恢复/不能恢复），没有计时 RTO 具体是几秒几分钟。在混沌测试里 Redis FLUSHALL 后恢复是成功的，但没有标准化的 RTO 指标。

## 评委 D：前端工程师（10y+）

### Q1：前端怎么保证排名一致？客户端会不会看到不同的结果？

> 服务器权威。客户端不做任何出价决策——出价后状态是 `pending`，最终态 100% 来自服务端 HTTP 响应或 WebSocket 事件。排名由 Redis 引擎单写者决定，通过 outbox→WebSocket 广播给所有客户端。每个事件带 `seq`，客户端用 seq 校验连续性：seq 跳变→触发快照恢复（`recoverFromSnapshot`）。所以所有客户端最终看到的是同一份服务端真相，只是到达时间有先后。

### Q2：倒计时怎么做到精确？客户端时钟不可信怎么办？

> 时钟漂移免疫方案（`domain.ts:416-429`）：
> 1. 从服务端响应获取 `server_time_ms` 和对应的本地 `Date.now()`
> 2. 倒计时计算：`remaining = end_at - server_time_ms - (Date.now() - synced_at)`
> 3. `Date.now() - synced_at` 是本地经过时间（单调），不依赖绝对时钟
> 4. 客户端手动调时间→不影响差值（经过时间不变）

> 倒计时只做显示，终态只来自服务端事件/快照。倒计时到 0 后客户端进入 `syncing` 状态等待服务端确认，不会自行宣布"已结束"。

**追杀：出价请求没有超时/AbortController，弱网怎么办？**

> 已修复（`main.tsx:55-67`）：`fetchWithTimeout` 封装了 `AbortController` + 8s 超时（`BID_REQUEST_TIMEOUT_MS = 8000`），超时后中断请求，用户可用同一 `client_bid_id` 安全重试（幂等保证）。

### Q3：氛围引擎怎么实现的？音效会不会卡？

> 6 种 cue（leading/outbid/extended/sold/recovering/social），每种有优先级：sold(100) > recovering(90) > extended(80) > outbid(60) > leading(50) > social(10)。高优先级抢占低优先级。

> 音效：优先使用预解码 WAV 音频缓冲（`loadAuctionSoundPack`），解码一次播放多次。WAV 加载失败→降级到程序化 Oscillator 生成（正弦/三角波，频率+增益包络）。触觉震动用 `navigator.vibrate()`。

> 去重：每个 cue 生成唯一键 `{auctionID}:{eventType}:{causeSeq}:{userScope}:{kind}`，已展示的不重复。页面隐藏/`prefers-reduced-motion` 时跳过。排行榜更新用 RAF burst mode（180ms 内的更新合并到一帧），防止高频动画抖动。

## 评委 E：产品经理（10y+ 直播电商）

### Q1：真实场景下，主播/商家最大的痛点是什么？你的系统怎么解决的？

> 三个核心痛点：
> 1. **信任**：买家怕假拍（托价/数据造假）→ 系统所有决策有 decision_basis（拒绝原因+当时价格），可审计；engine_seq 全序无空洞可以证明没有幽灵交易
> 2. **合规**：AI 生成内容不能承诺保真/升值→不安全词阻断 + 事实白名单 + 强制人审
> 3. **运营效率**：一个主播管多个拍品，同时要讲解/回答问题/监控异常→AI 自动解说 + 商品 Q&A + 哨兵告警分担运营压力

### Q2：误触二次确认怎么设计的？为什么不直接拦截？

> 竞拍场景下"大额出价"可能是真实意愿（抢心切），直接拦截会让用户愤怒。所以用二次确认：当出价金额超过当前价一定阈值（`fat_finger_threshold`）时，返回 `FAT_FINGER_CONFIRM_REQUIRED` + 30 秒 Redis token。用户确认后，系统**用当前价重跑全部守卫**（`engine.go:415+` confirm 脚本），不是无脑放行旧金额。如果确认期间有人出了更高价，你的确认会重新校验是否仍然有效。

**追杀：天价出价没有绝对上限？**

> 坦白：如果商家没设封顶价且没设误触阈值，一个超大但符合网格的金额会被直接 ACCEPT。应该在 admission 层加一个可配置的绝对上限或"相对当前价 N 倍"的 sanity bound。目前没做。

### Q3：1000 人同时出价的场景，真实直播间会这样吗？

> 会的。珠宝/奢侈品直播拍卖最后几秒是竞争最激烈的时刻。抖音/快手头部珠宝主播单场观看 10w+，高价值拍品最后倒计时围观几千人，其中几百到上千人同时点出价是真实场景。这也是为什么反狙击延时这么重要——最后一秒出价的人太多，如果不延时就不公平。

## 通用防守策略

### 被问到不会的问题

> "这个我没实现/没测过，如果要做的话我的思路是……"

### 被质疑过度设计

> "承认 brief 只要求 demo。但 brief 的三个挑战（毫秒级 + 零漏洞 + 高并发）本身要求决策链路有有序、可重放、可对账的 WAL。我选择了认真对待这些挑战，而不是打折完成。"

### 被追问是否独立完成

> 指到具体代码行号 + 解释设计取舍。能说出"我最开始用 PG 行锁，测试后发现 p99 太高才改成 Redis Lua"这种**演进过程**的人，一定是真做的。

### 被问"如果再做一次会改什么"

> 1. 拆 `engine.go` 单文件
> 2. 加规则双实现 parity test
> 3. 前端出价加超时
> 4. AI 加多 provider failover
> 5. 跑 RF=3 多副本压测

## 8 分钟节奏建议

| 时间 | 预期 |
|------|------|
| 0-2 min | 架构师/后端问热路径设计 |
| 2-4 min | 后端追问幂等/一致性细节 |
| 4-6 min | 前端/产品问用户体验/业务场景 |
| 6-8 min | 运维问测试证据/性能数字/容灾 |

评委通常会顺着你暴露的"诚实边界"追问——这不是坏事，说明你的自我评估和他们一致。如果评委开始问"如果给你更多时间会做什么"，说明基本面已经通过了，在探你的成长空间。
