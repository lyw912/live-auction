## 2. 真实架构（从代码反推，而非看图）

### 2.1 热出价路径（已逐行确认是默认生效路径，不是开关后的影子代码）

```
HTTP /bids
  → 网关：鉴权 / 房间 / ACL 预热 / admission 限流 / 幂等门（Idempotency-Key 必须 == client_bid_id）
  → redisengine.Engine.PlaceBid → placeBidWithSource
       └─ 单段原子 Lua（KEYS=[state, idem, pending, log_stream, acl]）：
            幂等回放（请求哈希冲突检测）→ 状态自举(缺失则 RECONCILING) → 完整性校验
            → paused/RECONCILING/requires_postgres 闸门 → 非 ACTIVE 拒绝
            → 脚本内原子 ACL 校验（无需额外 RTT）
            → 超时(now>end)拒绝 → 自我领先拒绝 → 封顶判定
            → base+increment 最小价/网格校验 → 误触(fat-finger)二次确认
            → engine_seq++（拒绝也消耗序号 = 全序无空洞）
            → 封顶=成交(SOLD)/否则反狙击延时(带 absolute_end_ms 硬顶)
            → XADD 决策流 + 写幂等结果 + pending（同一原子操作内）
  → triggerRelayForAuction（非阻塞）→ group-commit relay：XREAD→Kafka AppendBatch(acks=all)→标记 KAFKA_ACKED→唤醒 latch
  → HTTP 返回 ENGINE_ACCEPTED/REJECTED/SOLD + durability_status(KAFKA_ACKED 或降级 ENGINE_DURABLE) + settlement_status
  → 结算 Worker：消费 Kafka 决策 → 幂等落 PG（唯一约束 + engine_seq CAS）→ 建单 → outbox
  → Reconciler：比对 Redis/Stream/PG/event_seq，漂移则暂停并写异常
```

**为什么我确信这是默认路径而非花架子（关键证据）：**
- `config.go:139` 默认 `BidEngineMode: "redis_ledger"`；`bid_lane.go:58-59` 空值即 `redis_ledger`；`auction_handlers.go:736-738` 默认 redis_ledger。
- `.env:67` 注释写明：“Bid engine is the Redis hot ledger by default; **do not set BID_ENGINE_MODE** for normal local/demo runs.”
- `router.go:102` `engine := redisengine.New(deps.Postgres, deps.Redis, ledger)` 真实装配进网关。
- `cmd/server/main.go` 启动时 `go` 起：outbox relay、AI 解说 worker、**Kafka 结算 worker（主+多副）**、scheduler runner（带 fencer）。机器是真转的。
- `PlaceBidPostgresLegacyForTests`（`bid.go` 符号表）——PG 行锁路径已被显式降级为“仅测试/遗留”，命名诚实。

> 架构师视角第一印象：**把架构图摆出来 + 追问“为什么热路径不是 PG 行锁”，本项目能在 `docs/current/architecture.md:6` 给出教科书级回答**——“1000 个最后一秒竞争同一行，行锁串行化无法做到 sub-50ms p99”。这句话本身就说明作者**理解瓶颈来自哪里**，而不是堆中间件。

### 2.2 决策 Lua 的工程亮点（我亲自读完两段脚本，`engine.go:63-560`）

1. **幂等且防滥用**：`existing[1] ~= request_hash → IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST`；`requestHash(auctionID,userID,clientBidID,amount)` 含 user 与 amount，且 `Idempotency-Key` 必须等于 `client_bid_id`（`engine.go:placeBidWithSource:23`）。**跨用户重放他人 client_bid_id → 哈希不符被拒；重放时偷改金额 → 同样被拒。** 直接命中宣讲版“绝不允许一笔出价扣两次钱”。
2. **失败关闭**：状态缺失/不完整 → `RECONCILING`（`engine.go:96,165`），绝不凭空 ACCEPT。
3. **每个拒绝都有决策时刻依据**：`decision_basis{previous_price, required_min_price, current_price, reason, engine_seq}`（`engine.go:226-233,284-293`）。这正是 PTS-1B 合同要求的“reject 必须有 decision-time basis”。
4. **反狙击 + 反机器人**：延时不仅 10–30s 窗口判定，还有 `absolute_end_ms` 硬顶（`engine.go:362-364`），注释明确写“防止 bot 每 29s 出价无限续命”。**这是绝大多数候选人不会想到的攻击面。**
5. **engine_seq 全序**：拒绝也 `engine_seq++`（`engine.go:200`）→ 序号无空洞、可对账。
6. **误触两步确认**：`FAT_FINGER_CONFIRM_REQUIRED` + Redis pending token，二次确认时**用当前价重跑全部守卫**（`engine.go:415-` confirm 脚本）——不是无脑放行旧金额。
7. **隐私**：隐藏代理最高价/确认中金额不入快照/outbox/WS（`architecture.md:114-116` 合同 + 代码里 winner 在 AI 侧 mask）。

> 这一段 Lua 的质量，**资深后端随便挑 3 个细节（幂等冲突、拒绝也消耗序号、absolute_end 硬顶）一问，就能确认这是“真懂分布式正确性”的人写的，不是抄的。**

### 2.3 分布式正确性子系统（非 hand-wavy，已确认方法族真实存在）

- **Group-commit + 熔断**：`kafkaAckRegistry` in-process latch（`engine.go:645`）、`waitKafkaAck` 在 `kafkaRelayUnhealthy` 时跳过 latch（`engine.go:871-873`）、`relayAuctionLogBatch` 失败即 `kafkaRelayUnhealthy.Store(true)`（`engine.go:2443-2444`）。**Kafka 故障降级到 `ENGINE_DURABLE` 零额外尾延迟**，这是对“fail-fast wakeup + circuit breaker”的真实实现。
- **结算/重建 Worker**：`settleAcceptedBatchPrefix`/`settleRejectedBatchPrefix`/`retryOrDLQ`/`ProcessReconcile`/`recoverPendingDecisions`/`rebuildRedisFromCheckpoint`/`writeRedisStateSnapshot`/`upsertEngineCheckpointFromCurrentState`（`engine.go:2662-3855`）——**完整的“消费→幂等落库→DLQ→重建快照”闭环**。
- **Reconciler**：`reconcile/checker.go:17-26` 定义了 `SNAPSHOT_MISSING/SEQ_DRIFT/FIELD_DRIFT/HISTORY_GAP/DB_EVENT_SEQ_DRIFT/REDIS_DB_RECONCILIATION_DRIFT` 等**分型漂移**，发现即写异常。
- **exactly-once 的诚实表述**：`architecture.md:58-65` 明说 `segmentio/kafka-go` 无幂等 producer（未实现 KIP-185），因此**不吹 exactly-once**，而是“at-least-once WAL + 幂等消费者（PG 唯一约束 + engine_seq CAS）= effectively exactly-once，PG 是 exactly-once 边界”。**Tavily 核验：这正是 Confluent/业界的标准口径**（真正 EOS 需幂等 producer+事务；否则用幂等消费者去重是公认替代方案）。**敢于不吹 exactly-once、并准确说明边界，是高级信号——它把“懂”和“背名词”区分开了。**

## 4. AI 全栈轴（这是“AI 课题”，必须单独评）

> 评分维度一原文含“开源模型调用（**可选**）”。本项目把“可选”做成了**端到端、provider-first、强护栏**的真集成。

## 10. 答辩护身符（评委必问 × 标准答案）

- **“热路径为什么不是数据库？”** → 同一拍品行级争用，行锁串行化无法 sub-50ms p99；改为 Redis 单写者原子 Lua 决策，PG 退居结算/审计/订单真相。
- **“你说 exactly-once？”** → 不，我们是 **at-least-once WAL + 幂等消费者**（PG 唯一约束 + engine_seq CAS）= **effectively exactly-once，PG 是 exactly-once 边界**；segmentio/kafka-go 无幂等 producer，我们不吹。
- **“Redis 挂了/被 FLUSHALL 怎么办？”** → 暂停受影响拍品 → 从 Kafka 高水位 + PG 结算态重建 → 校验 epoch/seq/价/胜者/终态/待结算覆盖 → 校验通过才恢复；恢复期用户看到“恢复中/暂停”，**禁用危险出价，不给假成功**。
- **“1000 并发最后一秒怎么保证最高价唯一胜者？”** → 单写者原子 Lua 串行化决策 + engine_seq 全序（拒绝也消序号）+ 校验器在 PG 真相上对账 `winner==highest_accepted`。
- **“一笔出价会不会扣两次？”** → 幂等键必须 == client_bid_id；请求哈希含 user+amount；重放返回同结果，异哈希判冲突；结算端唯一约束 + CAS。
- **“为什么 S1 是 ENGINE_DURABLE 而不是 KAFKA_ACKED？”** → kafka_ack 模式下 latch 超时/Kafka 故障熔断会降级到 Redis-AOF-local 的 ENGINE_DURABLE，**决策已先写 Redis AOF+Stream+幂等记录**，relay 异步补 ACK，事后对账显示全部已结算且 lag=0——是优雅降级，不是丢数据。
- **“为什么不用 PG 行锁更简单？”** → 见第一条；且我们保留了 PG 行锁路径作为**仅测试/遗留**对照（`PlaceBidPostgresLegacyForTests`），证明我们权衡过。
- **“为什么要 Kafka，是不是过度设计？”**（最锋利的一问）→ 直接承认 brief 只要求 demo，但**毫秒级 + 零漏洞 + 强一致**这三个 brief 自己提出的挑战，要求决策必须有**有序、可重放、可对账、可 fail-closed**的持久 WAL；Kafka 是承担这个职责的最标准件。**“我们是为 brief 的挑战而非为简历堆中间件”**——并用 reconciler/混沌证据佐证。
