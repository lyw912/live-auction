# Part A — 决策 Lua vs PG legacy：逐分支等价性证明

## A.0 两条路径的定位（先厘清，避免误判）

- **Lua 决策引擎**（`redisengine` 内嵌脚本）= **线上唯一热路径**（`config.go:139` 默认 `redis_ledger`；`router.go:102` 装配）。
- **PG legacy**（`evaluateAndApplyBid`/`applyAcceptedBid` + `rules.go` 的 `ClassifyBidAmount`/`CalculateExtension`）= **仅测试/遗留**（入口符号即名 `PlaceBidPostgresLegacyForTests`）。
- 因此“等价性”的现实意义是：**PG legacy 的测试断言能否代表线上 Lua 的真实行为？** 答案是——**核心规则分类等价，但反狙击延时公式不等价**（下证）。

## A.2 唯一实质性背离：反狙击延时公式（已用真实测试坐实）

**两套公式：**
- PG legacy（`rules.go:119-131`）：`candidate = serverNow + extendBy`，且仅当 `candidate > end` 才延时 → **从“出价那一刻”起保证还剩 `extendBy` 秒**（eBay 经典语义）。
- 线上 Lua（`engine.go:357-368`）：`candidate = end_at + extend_by`，必 `> end`（`extend_by≥10`），再被 `absolute_end_ms` 硬顶 clamp → **在“当前 end”上固定加 `extend_by`**，与出价落在窗口何处无关。

**测试坐实（关键）：** 线上软关闭测试 `TestRedisLedgerConcurrentSoftCloseExtendsOnlyOnce` 断言
```go
// engine_integration_test.go:526
wantEndAt := time.UnixMilli(originalEndAt.UnixMilli()).UTC().Add(10 * time.Second) // = end + extendBy
```
即 **end 锚定**。若改用 PG 的 `now+extendBy`，当出价在 end 前 t 秒落地时结果为 `now+10 = end-t+10 ≠ end+10`，断言会失败。

**为什么这是真问题（而非吹毛求疵）：**
1. **同一组出价序列，两条路径会算出不同的 end_at**，进而可能影响“最后一秒还能再来几手”→ 极端竞争下甚至影响最终赢家。
2. Lua 注释 `engine.go:303` 自称“strictly mirrors the PG lane's ClassifyBidAmount”——**这句话对“规则分类/误触”成立，但对“延时公式”不成立**，属于**被坐实的注释过度声明**。
3. **无任何 parity 测试横向比对两条路径**（全仓只有 `deposit_parity_test.go` 比对押金，无出价/延时 parity）。`CalculateExtension`（`now+by`）当前**只被 PG legacy/测试触达**，线上不可达——也就是说，**一段会产生不同业务语义的代码，仍以“参考实现”的姿态留在 `rules.go` 且被测试当真。**

**结论：** 线上行为本身（end 锚定 + 绝对硬顶）**自洽、可验证、且更确定**（`soft_close_no_stacked_subwindow_extension` 门禁正是按 end 锚定写的，见 B.28）。风险不在“线上算错”，而在“**两份实现各自为政、注释过度声明、无 parity 守护**”——这正是主报告 §8 中等项“规则双实现漂移”的**具体实锤**。

**建议（任选其一，按成本递增）：**
- **(最低成本)** 修正 `engine.go:303` 注释，明确“仅规则分类/误触镜像 PG；延时公式以 Lua 为准（end 锚定 + absolute_end）”；并在 `rules.go:CalculateExtension` 上加注释标注“仅 PG legacy/测试，线上语义见 Lua”。
- **(推荐)** 加一个 **parity property test**：对随机 `(state, bid)` 同时喂 `ClassifyBidAmount` 与 Lua，断言 `(decision_class, price, terminal)` 一致（延时单独按各自语义断言或显式标注差异）。
- **(最彻底)** 删除 `CalculateExtension`/PG legacy 延时，或由同一份 spec 生成 Go 参考与 Lua，使 Lua 成为唯一真相源。

## A.3 等价性总裁定

| 维度 | 裁定 |
|---|---|
| 5 条核心规则（0 起拍/加价网格/封顶成交/封顶以上拒/低价拒） | ✅ **语义等价**（同逻辑同顺序） |
| 自我领先、误触阈值+基准、终态恰一单 | ✅ **等价** |
| 幂等（dup 同结果 / 异哈希冲突） | ✅ **结果等价**（DB 唯一约束 vs Redis idem_key，机制不同） |
| 失败关闭闸门 + 脚本内 ACL + 全序 engine_seq | 🟦 **Lua 独有增强**（PG 无，不矛盾） |
| **反狙击延时公式** | ❌ **实质背离**（`now+by` vs `end+by`），**无 parity 守护**，注释过度声明 |

> 一句话：**“零漏洞”主张在规则分类层成立；唯一被坐实的工程隐患是延时公式的双实现漂移——线上自洽，但缺少跨实现一致性守护，且有一处过度声明的注释。** 这是一个**可在 30 分钟内闭合**的诚实缺口，不动摇地基。

## B.6 这套门禁的“评委级”意义

1. **校验对象是 PostgreSQL 落库真相 + Redis/Kafka 交叉，而非 HTTP 200 计数**——直接呼应合同“Do not treat HTTP status alone as auction outcome”。
2. **每条不变式都能指回一段原子机制**（不是“跑完看着对”）：最高价胜者←单写者原子决策；拒绝有据←decision_basis；无空洞总序←每决策 engine_seq++；恰一单←唯一约束+幂等结算。
3. **P0 任一 FAIL 即整体 FAIL**（`:1338`）——无“差不多就行”的灰度。
4. **诚实边界**（用户已声明可接受）：这些门禁证明的是**单节点正确性**；`kafka_consumer_group_lag_zero` 等只在“跑完等待收敛后”成立，**不证明 RF=3/多 AZ**；S3 的 fanout p99 缺原始采样日志。**答辩时应主动声明“代码可证的正确性”与“需重跑的性能数字”的分界**，不要让评委自己发现。

## 附录小结（给评委的两句话）

- **等价性**：线上 Lua 与 PG legacy 在 5 条核心规则与幂等/终态上**语义等价**；**唯一实质背离是反狙击延时公式（`now+by` vs `end+by`），且无 parity 守护、有一处过度声明注释**——线上自洽，但属可被坐实的双实现漂移，30 分钟可闭合。
- **门禁**：35 条门禁**逐条可追溯到原子机制并指回 brief/合同条款**，校验 PG 落库真相而非 HTTP 状态，P0 零容忍——这是 SRE 级而非学生级的正确性工程；其诚实边界（单节点、需重跑性能）已被项目自己标注。
