## 5\. 端到端使用流程

1. **商家发品**：PC 端上传商品图片→AI Copilot 自动生成标题/卖点/合规标记→人工审核确认

2. **配置规则**：设置起拍价\(支持0元\)、加价幅度、封顶价\(自动校验可达性\+网格对齐\)、延时策略、押金比例

3. **排期开拍**：排期后规则冻结→到时自动开拍→H5 端用户进入直播间看到实时竞拍

4. **实时竞价**：用户出价→服务端原子 Lua 决策（幂等/规则/反狙击全在一次原子操作内）→结果秒级广播→排行榜实时更新

5. **氛围反馈**：领先/被超越/延时/落槌全程分阶段动效\+音效\+触觉；倒计时精确到毫秒（服务器时间锚定，时钟漂移免疫）

6. **成交结算**：封顶或倒计时结束→Kafka 结算→PG 建单→mock 支付→订单详情

7. **复盘运营**：AI 生成竞拍复盘摘要\+高光片段\+定价建议→商家 PC 端查看

## 10\. 关键工程难点与解决方案

>

### 难点 1：千人最后一秒竞争同一行 — 出价决策 p99 ≤ 50ms

**遇到的问题：** 直播竞拍最核心的业务场景是"绝杀时刻"——拍品即将结束时，上千用户在最后一秒同时出价抢拍。项目早期我实现了完整的 PG\-Lane 路径（`SELECT ... FOR UPDATE` 行锁），在功能上完全正确。但当 1000 个用户同时竞争同一个 `auction` 行时，行锁排队导致 p99 劣化到数百毫秒以上。连接池调优、缩短事务、准入限流都试过，只能缓解无法根治——因为这是单行串行化的物理天花板。

**为什么选择 Redis Lua：** Redis 单线程天然串行化，但不需要锁等待。关键是我把**全部 12 项竞拍规则**（幂等检查、ACL 校验、反狙击延时、封顶成交、误触确认、自领检测、网格校验、时间校验等）下沉到一段 \~300 行 Lua 脚本内原子完成（`engine.go` 行 64\-406），一次 Redis RTT 完成所有决策。不像工业级秒杀方案只在 Redis 做库存扣量、业务逻辑仍在应用层——那种方案需要应用层和 Redis 之间多次往返，在竞拍场景下会被价格变化导致的重试放大。

**Kafka 不是装饰：** 决策完成后，Redis Stream 作为本地 WAL，Kafka relay 以 group\-commit 批量 `AppendBatch(acks=all)` 写入持久化层。如果 Kafka 故障，引擎内置的 `kafkaRelayUnhealthy` 熔断器零额外延迟降级到 `ENGINE_DURABLE`（Redis AOF 持久），不阻塞用户。

**PG 退居结算真相：** 结算 worker 消费 Kafka，通过 `engine_seq CAS`（`WHERE engine_epoch=$7 AND engine_seq=$6-1`）\+ PG 唯一约束实现 effectively exactly\-once。PG 不再是热路径瓶颈，但仍是结算、审计、订单的最终真相。

|维度|实测结果|
|---|---|
|**S1 p99**|23ms（ENGINE\_DURABLE）/ 58ms（KAFKA\_ACKED），1000 用户 505ms 窗口内一次性决策|
|**正确性**|41 条门禁全绿，264 accepted \+ 736 rejected = 1000 完整决策|

### 难点 2：分布式一致性 — 绝不允许一笔出价扣两次钱

**遇到的问题：** 引入 Redis \+ Kafka \+ PG 三层后，一个决策要经过 Redis Lua → Redis Stream → Kafka → PG settlement 四步才能落库。如果 Kafka 消费者在写入 PG 之后、提交 offset 之前崩溃（settlement worker SIGKILL），Kafka 会重新投递同一条消息。如果没有幂等保护，赢家就会被扣两次钱、生成两个订单——这是竞拍系统最不能容忍的 bug。

**三层幂等链（每一层都是被具体故障场景逼出来的）：**

|层|机制|防什么|
|---|---|---|
|Redis|`idem:{clientBidID}` key 存 `request_hash`|客户端重试/网络重放 → 同哈希回放原决策，异哈希拒绝为冲突|
|Kafka|`engine_seq` 全局递增，每个决策（含拒绝）都占一个序号|保证全序可对账，无空洞|
|PG|`UNIQUE(auction_id, user_id, client_bid_id)` \+ `engine_seq CAS`|Kafka at\-least\-once 重投 → PG 唯一约束兜底，不产生第二笔业务效果|

**Reconciler 不只是对账，是自动刹车：** 每 30 秒对每个活跃拍品执行 8 项不变式校验（序号完整、赢家/价格匹配、结算无缺失、outbox 覆盖等）。发现异常不只是告警——自动暂停引擎（`engine_paused=true`），禁止新出价，直到修复确认后才恢复。

**实测证明：** S4 混沌测试中 `08-settlement-idempotency` 场景向结算 worker 投递同一条 Kafka 消息 3 次，验证结果：精确 1 条结算记录、1 条出价记录、1 个订单、1 条 outbox 投递，零重复业务效果。

### 难点 3：Redis 丢失恢复 — 不给假成功

**遇到的问题：** Redis 是内存数据库，`FLUSHALL`、OOM 驱逐、机器宕机都会导致热态丢失。在开发 S4 混沌测试时，我发现如果 Redis 状态丢失后引擎仍然对外声称"已接受"，用户会看到假的中标信息，但 PG 里没有对应的结算记录——这比系统宕机更危险，因为用户以为自己赢了但实际上什么都没发生。

**失败关闭（fail\-closed）是唯一正确选择：**

1. 检测丢失：Lua 脚本发现 Redis state key 不存在时，不猜测、不用旧数据凑，直接返回 `RECONCILING`

2. 暂停拍品：设置 `engine_paused=true`，用户看到"恢复中"，禁用出价按钮

3. 从 Kafka 高水位 \+ PG 结算状态重建：`rebuildRedisFromCheckpoint` 读取 `auction_engine_checkpoints` 表的 SHA\-256 校验快照，恢复完整 Redis 热态

4. 重建时递增 `engine_epoch`：旧 epoch 的 stale 决策在结算时被 CAS 拒绝，不会产生幽灵结算

5. 校验通过才恢复：8 项不变式全部 PASS 后 Reconciler 自动解除暂停

**实测证明：** S4 `redis-flush` 场景执行 `FLUSHALL` 后，故障窗口内 0 笔出价返回 `ENGINE_ACCEPTED`，RTO 2 秒自动恢复，所有结算记录与 Kafka WAL 精确匹配。

### 难点 4：前端实时体验 — 服务器权威 \+ 断线重连 \+ 氛围引擎

**遇到的问题：**

- **时钟问题：** 早期倒计时用客户端本地时间，用户改手机时间就能看到错误的倒计时，甚至看到"已结束"但实际还在拍卖

- **断连后乱序：** 移动端网络切换（WiFi→4G）后 WebSocket 断连，重连后如果只拿最新状态，中间错过的出价事件就丢了，用户看到价格跳变但不知道发生了什么

- **假状态危害：** 如果客户端在断连期间用本地缓存的"我是领先者"状态让用户误以为还在赢，用户可能放弃继续出价，结果输掉拍品

**解决方案（每个都针对具体问题）：**

|问题|方案|代码位置|
|---|---|---|
|**客户端时钟不可信**|倒计时 = `server_time_ms` \+ 本地经过时间推算，完全免疫手机时间篡改|`mobile-h5/src/main.tsx` serverTimeSyncedAt|
|**断连丢事件**|重连带 `last_seq`，服务端返回缺失的 seq 历史；如果 gap 太大则降级为快照恢复|`realtime/server.go` recoveryMessages|
|**假状态**|出价后 UI 置 pending，最终态 100% 来自服务端；断连/不确定→禁用出价按钮|`mobile-h5/src/main.tsx` recovering 状态|
|**重连风暴**|指数退避 \+ 抖动（`realtime.ts`），避免千人同时重连打垮服务|`mobile-h5/src/realtime.ts`|
|**氛围同步**|6 种 cue（领先/被超越/延时/落槌/恢复中/社交）× 优先级 × 去重，音效/动效/触觉分阶段触发|`mobile-h5` atmosphere engine|

### 与同类项目 / 传统方案 / 工业级系统架构对比

多数竞拍/秒杀类项目（包括本项目早期 PG\-Lane 基线）使用 **PostgreSQL 行锁串行化** 作为核心决策点。本项目经过真实压测证伪后，演进为 **Redis Lua 单写者 \+ Kafka WAL \+ PG 结算** 的三层架构。以下是与传统方案和工业级系统的直接对比：

|对比维度|PG\-Lane / 传统行锁方案|淘宝/京东秒杀系统（工业级参考）|本项目（Redis Lua \+ Kafka \+ PG）|
|---|---|---|---|
|**热路径决策**|PG `SELECT ... FOR UPDATE` 行锁串行|Redis Lua 原子扣量 \+ hash tag 分槽（Thoughtworks/阿里云 Tair 公开方案）|Redis Lua 单写者原子决策：一段 300 行 Lua 脚本完成幂等→12 项规则校验→决策→XADD 写流→idem 写回，一次 RTT|
|**千人争抢 p99**|行锁排队 → p99 数百ms\~秒级|未公开具体延迟指标；CrackingWalnuts 50K bids/s 设计给出 p99 200ms 目标|**S1 实测 p99 23ms**（ENGINE\_DURABLE）/ **58ms**（KAFKA\_ACKED），1000 用户在 505ms 窗口内一次性决策|
|**吞吐瓶颈**|单行锁串行；池化/短事务只缓解|Redis 单线程 \+ 按商品分片；但公开方案中 Redis 仅做库存扣量，业务逻辑在应用层|Redis 内完成**全部业务规则**（反狙击延时/封顶成交/误触确认/自领检测/ACL/网格校验），零应用层往返|
|**持久性分层**|事务即持久（一层）|Redis 扣量 \+ MQ 异步落库 \+ 定期 CDC 对账（阿里云方案）|**四层显式持久**：Redis AOF → Redis Stream WAL → Kafka acks=all group\-commit → PG 结算；每层有独立 response 字段和恢复路径|
|**故障降级**|PG 宕 = 全不可用|Redis Cluster 多副本 \+ 同城异地多中心（成本极高）|Redis 宕→**fail\-closed 暂停**→Kafka/PG 重建（epoch CAS 隔离旧决策）；Kafka 宕→熔断器零延迟降级 ENGINE\_DURABLE；PG 宕→热路径不受影响|
|**幂等/防重**|PG 唯一约束（一层）|Redis history key 幂等 \+ 应用层去重（Thoughtworks 方案）|**三层幂等链**：Redis idem key（request\_hash 区分回放/冲突）\+ Kafka WAL \+ PG `UNIQUE(auction_id, user_id, client_bid_id)` \+ engine\_seq CAS|
|**对账机制**|单一数据源，无需对账|定期 CDC 对账（阿里云方案）|**实时 Reconciler**（30s 周期）交叉比对 Redis state/Stream/Kafka/PG/outbox 的 8 项不变式；异常→暂停→告警|
|**正确性验证**|无系统性验证|内部压测平台（不对外公开）|**41 条自动化门禁**（28 PG 不变式 \+ 7 Redis \+ 4 Kafka \+ 2 reject），全部校验 PG 落库真相，P0 任一 FAIL 即整体 FAIL|
|**扩展路径**|分库分表（改造成本极高）|Redis Cluster \+ 多中心|按拍品分片：Redis Cluster `{auctionID}` hash tag \+ Kafka 按 auction\_id 分区 \+ WS gateway 按 room 路由|
|**工程复杂度**|低|极高（大厂专属基础设施）|高：但完全落地且可运行，非文档摆设|

> **为什么不直接用 PG？** 当 1000 个最后一秒出价竞争同一个 `auction` 行时，行锁排队使 p99 退化到数百毫秒以上。这与业界共识一致——阿里云 Tair 秒杀方案和 Thoughtworks 高并发设计均明确指出"DB 单行锁在高并发下无法承载"。连接池调优、缩短事务、准入限流都只能缓解，无法根本解决单行串行化的天花板。CrackingWalnuts 的 50K bids/s 拍卖系统设计也得出相同结论：PG\-only 方案上限约 500 bids/s，超过需要 Valkey\(Redis\) \+ Kafka 分层。

> **与工业级方案的差异与亮点：** 淘宝/京东秒杀系统的 Redis Lua 通常只做库存扣量（约 20 行 Lua），业务规则仍在应用层；本项目将**全部 12 项竞拍规则**（幂等/ACL/反狙击/封顶/误触/自领/网格校验/时间校验等）下沉到一段 300 行 Lua 脚本内原子完成，消除了应用层与 Redis 的多次往返。同时，工业级系统的对账通常是定期 CDC 批量比对，本项目实现了 **30 秒周期实时 Reconciler \+ 8 项不变式自动校验**，异常时自动暂停引擎而非仅告警。

### 亮点 1：不是 demo，是失败关闭的实时交易内核

多数同类项目止步于"React\+WebSocket\+MySQL 起拍/加价/倒计时"。本项目真正落地了 **Redis Lua 单写者原子决策 → Kafka 有序决策 WAL/Fence → PostgreSQL 结算真相 → Reconciler 校验** 的 fail\-closed 链路，且**默认配置即跑通全链路，不是文档摆设**。每一个中间件都对应一个被想清楚的失败模式——Kafka 不是简历装饰，而是决策 WAL \+ 故障证据 \+ 结算重放源。

### 亮点 2：AI 做助手，不做决策者

在电商竞拍场景下，AI 的正确定位是**增信息密度与运营效率，绝不污染交易真相**。本项目的 AI 永远不碰钱/胜者/终态：选品强制人审、解说事实白名单、哨兵永不自动封禁、Q\&A 只引用审核属性。Provider 失败→确定性模板降级，job 记录完整审计轨迹。**对一个电商竞拍系统，这是对的工程价值观。**

### 亮点 3：正确性可证明，不是"跑完看着对"

35 条 PTS 正确性门禁（28 不变式 \+ 7 基础设施），校验对象是 **PG 落库真相 \+ Redis/Kafka 交叉**，不是 HTTP 200 计数。每条不变式可追溯到一段原子机制：最高价胜者←单写者原子决策；拒绝有据←decision\_basis；无空洞全序←engine\_seq\+\+；恰一单←唯一约束\+幂等结算。**P0 任一 FAIL 即整体 FAIL，无"差不多就行"。**

## 12\. 其余材料

### 12\.0 性能 × 正确性 × 鲁棒性 测试

多数竞拍/秒杀项目只关注单一维度——要么追求"TPS 多高"（但没验证正确性），要么展示"有 Redis 有 Kafka"（但没验证故障下会不会出错）。本项目的测试体系（S1\-S5）设计的核心目标是：**每一个性能数字背后都有正确性证明，每一个正确性声明都经过故障注入考验。**

|维度|含义|如何验证|对应场景|
|---|---|---|---|
|**性能/速度**|出价决策足够快，用户体验流畅|1000 人最后一秒 p99 ≤ 60ms；万人围观广播 p99 \< 500ms|S1、S2、S3|
|**一致性/正确性**|赢家一定是最高价、拒绝都有据、序号无空洞、绝不扣两次钱|41 条自动化门禁校验 PG 落库真相 \+ Redis/Kafka 交叉验证|每个 S 都带正确性校验|
|**鲁棒性/稳定性**|Redis/Kafka/PG 任一宕机不给假成功、不丢数据、自动恢复|SIGKILL \+ FLUSHALL \+ Toxiproxy 网络故障注入，200 并发下验证 fail\-closed|S4、S5|

**关键设计原则：一个延迟数字如果没有正确性校验器输出，就不是成功证据。** 这意味着 S1 跑完 p99 23ms 后，还必须验证 `winner == highest_accepted`、`engine_seq` 无空洞、所有 reject 都带 `decision_basis`、Kafka lag = 0、outbox 全部投递——**41 条门禁任一 FAIL 即整体 FAIL**。

#### S1 — 绝杀时刻（验证维度：性能 \+ 正确性）

**业务场景：** 拍品即将落槌，1000 个用户在最后一秒同时出价。谁出价最高谁赢，所有输家必须在毫秒级得到明确的拒绝理由。

**为什么需要这个测试：** 这是整个系统最难的一刻——所有请求在 500ms 内涌入同一个热点。如果引擎扛不住，用户会看到超时或错误；如果引擎快但不正确，可能出现低价中标或同一拍品卖给两个人。

**测试脚本逻辑：**

|步骤|逻辑|关键实现|
|---|---|---|
|1\. 预加载身份|从 CSV 读取 1000 个预签发 JWT session（非测试中登录）|`s1-s5-1000-user-sessions.csv`，reset 脚本预种到 Redis auth/ACL 缓存|
|2\. 计算出价金额|每个 VU 出价 = 当前价 \+ \(1\~5\) × 加价幅度（确定性分散，模拟真实用户选不同金额）|Groovy: `steps=[1,1,1,2,3,4,5]`, `k = steps[(vu*2654435761L & 0x7fffffff) % 7]`|
|3\. 同步屏障|所有 VU 对齐到同一个墙钟时间点，然后在 500ms 窗口内按 rank 偏移释放|`contention_release_window_ms=500`, offset = `globalRank % 500` ms|
|4\. 发送出价|POST `/api/auctions/auc_live/bids`，携带 `client_bid_id` \+ `Idempotency-Key`|HTTP body: `{client_bid_id, amount_cents, idempotency_key}`|
|5\. 断言最终决策|响应必须是 `DECIDED`（非 202 待处理），`durability_status` 必须是 `KAFKA_ACKED` 或 `ENGINE_DURABLE`|Groovy PostProcessor 校验，202/pending 标记为失败不计入 p99|
|6\. 保持 VU|出价后 VU 持续存活到 60s，防止 PTS 提前关闭线程|`Thread.sleep(startedAt + 60000 - now)`|

**测试环境与参数：**

|参数|值|说明|
|---|---|---|
|压力源|阿里云 PTS VPC 内网|消除公网延迟干扰|
|压力 IP|2 台（⌈1000/500⌉）|每台 500 VU|
|VU 数|1000|每人出价 1 次|
|循环次数|1（PTS 控制台指定）|不重复，one\-shot burst|
|采样率|100%（judge\-forensics 模式）|每条请求可追溯|
|拍品配置|起拍价 0，加价 5000 分，无封顶|允许多人被接受（价格阶梯）|
|运行时 profile|`kafka_ack`（默认生产模式）|响应等待 Kafka 确认|

**测试结果：**

|指标|目标|实测（UIPAX7JG）|说明|
|---|---|---|---|
|**出价决策 p99**|≤ 60ms|**58ms**（max 67ms）|PTS 100% 采样 `elapsedTime`，KAFKA\_ACKED 响应边界|
|**总决策数**|1000|1000（264 accepted \+ 736 rejected）|每个出价都得到最终决策|
|**赢家正确**|highest == winner|✅ PASS|`auction_winner_matches_highest_accepted` 门禁|
|**序号完整**|1\.\.1000 无空洞|✅ PASS|`engine_seq_complete` 门禁|

#### S2 — 正常竞价（验证维度：稳定性 \+ 正确性）

#### S3 — 万人围观（验证维度：性能 \+ 稳定性）

**业务场景：** 一个热门拍品，3000\+ 人在直播间实时观看。每当有人出价成功，所有观众必须在 1 秒内看到新价格。这是直播竞拍的核心体验——观众看不到价格变化，就不知道该不该出更高的价。

|出价 VU|998|
|读请求 VU|499|
|采样率|1%|

#### S4 — 故障韧性（验证维度：鲁棒性 \+ 正确性）

**业务场景：** 拍卖正在进行中，Redis/Kafka/PG 突然宕机。200 个用户正在出价——系统会不会给出假的"中标"？会不会把同一笔钱扣两次？

**为什么需要这个测试：** 性能再好，如果故障时给了假成功，用户以为自己赢了但结算里没有记录——这是竞拍系统最严重的事故。S4 证明的是：**故障时宁可慢/暂停，绝不给假成功。**

**测试脚本逻辑（****`s4-concurrent-fault.js`**** \+ ****`run-pts-1c-concurrent-fault.sh`****）：**

4. 等 5 秒稳定后，注入故障（SIGKILL/FLUSHALL/Toxiproxy）

5. 故障持续 5 秒

6. 恢复故障（重启容器/清除 Toxiproxy）

7. 等待 k6 结束 \+ 结算收敛

8. 运行 41 条门禁校验器

#### S5 — 断连重连（验证维度：鲁棒性 \+ 正确性）

**业务场景：** 用户在出价过程中手机网络切换（WiFi→4G），WebSocket 断连，错过了几笔价格更新。重连后，用户看到的价格/赢家是否正确？中间错过的事件有没有丢？有没有重复？

**测试脚本逻辑（****`s5-reconnect-recovery.js`****）：**

每个 VU 的循环：连接 WS → 接收当前状态 → 主动断开 → 等待至少 3 笔新出价发生 → 用过时的 `last_seq` 重连 → 验证恢复到当前 seq \+ 无 gap \+ 无重复 \+ 价格与服务端一致。

**测试环境与参数：**

|参数|值|
|---|---|
|重连 VU|200（clean 模式）/ 50（Toxiproxy 网络模式）|
|出价源|5 VU × 10 bids/s 持续产生真实价格更新|
|持续时间|2 分钟|
|网络故障|Toxiproxy `reset_peer`（30% toxicity，模拟弱网随机断连）|

**测试结果：**

|模式|恢复次数|TTCS p99|恢复错误|Seq gap|重复 seq|真相不匹配|
|---|---|---|---|---|---|---|
|**clean 断连**|34,814|**87ms**|0|0|0|0|
|**Toxiproxy 弱网**|8,849|**341ms**|0|0|0|0|

服务端确认：21,574 次 `ws_reconnect` 事件，恢复来源分布：history=16,584, db=4,913, snapshot\_unavailable=77——证明恢复走了真实的后端恢复路径（Redis 历史回放 / PG 查询 / 快照降级），不是客户端假装成功。
